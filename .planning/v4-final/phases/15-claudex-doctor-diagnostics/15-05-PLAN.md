# Plan 15-05: CLI orchestrator + docs + phase close (DIAG-01, DIAG-08)

## Objective

Wire the four check modules from plans 15-02..15-04 into a single `bun run doctor` CLI, implement output formatting (default table + `--json`), apply the exit-code contract (DIAG-08), update README with a Diagnostics section (DIAG-01), and close Phase 15 with the canonical state-file updates and commit pattern.

## Why this is the final wave

Plans 15-02 / 15-03 / 15-04 produce per-check modules that don't import each other. This plan imports all four, registers them with the runner from 15-01, and drives output + exit codes. Splitting the CLI off into the final wave means:
- The five check modules can land in any order and in parallel during Wave 2.
- The CLI plan's tests can use the real check modules (no mocks needed for the orchestration test).
- Phase-close work (state files, traceability updates, SUMMARY.md, vesna gate) lives in one place at the end rather than smeared across plans.

<task id="01-format-module">
**Create `src/diagnostics/format.ts`** — output formatters.

Two pure functions, no I/O:

```ts
import type { DoctorReport, CheckResult } from './types.js';

const SYMBOL: Record<CheckResult['status'], string> = {
  pass: '✓',
  fail: '✗',
  warn: '⚠',
};

export function formatHuman(report: DoctorReport): string {
  const lines: string[] = [];
  lines.push('Claudex Doctor — checking install health');
  lines.push('─'.repeat(50));

  for (const c of report.checks) {
    const sym = SYMBOL[c.status];
    const left = `${sym} ${c.name.padEnd(18)}`;
    const right = `${c.detail.padEnd(28)} (${c.durationMs}ms)`;
    lines.push(`${left} ${right}`);
    if (c.status !== 'pass' && c.remediation) {
      lines.push(`  → ${c.remediation}`);
    }
  }

  lines.push('─'.repeat(50));
  if (report.overall === 'pass') {
    const warns = report.checks.filter((c) => c.status === 'warn').length;
    lines.push(warns === 0
      ? 'All checks passed. Claudex is healthy.'
      : `All checks passed (${warns} warning${warns === 1 ? '' : 's'}). Claudex is healthy.`);
  } else {
    const fails = report.checks.filter((c) => c.status === 'fail').length;
    lines.push(`${fails} check${fails === 1 ? '' : 's'} failed. See remediations above.`);
  }

  return lines.join('\n');
}

export function formatJson(report: DoctorReport): string {
  return JSON.stringify(
    { status: report.overall, checks: report.checks, startedAt: report.startedAt, durationMs: report.durationMs },
    null,
    2,
  );
}
```

Notes:
- Pure functions — no `console.log`, no `process.exit`. The CLI orchestrator calls them and prints.
- Symbols match `references/ui-brand.md` (`✓`, `✗`, `⚠`).
- Keep the table width modest. The pad-end choices (18 for name, 28 for detail) are tuned for the seven check names from CONTEXT.md sample output ("Bun version", "Ollama", "Reranker", "DB schema", "CC hooks", "Angel"). Adjust if a check name overflows.
- The JSON shape matches CONTEXT.md DIAG-08 example: `{ status, checks, ... }`.
</task>

<task id="02-doctor-cli">
**Create `src/cli/doctor.ts`** — the orchestrator entry.

```ts
#!/usr/bin/env node
/**
 * claudex doctor — diagnose install health.
 * Exit 0: all pass (warns OK). Exit 1: any fail. Exit 2: doctor itself crashed.
 */

import { runChecks } from '../diagnostics/runner.js';
import { formatHuman, formatJson } from '../diagnostics/format.js';
import { checkBun } from '../diagnostics/check-bun.js';
import { checkOllama } from '../diagnostics/check-ollama.js';
import { checkReranker } from '../diagnostics/check-reranker.js';
import { checkDb } from '../diagnostics/check-db.js';
import { checkHooks } from '../diagnostics/check-hooks.js';
import { checkAngel } from '../diagnostics/check-angel.js';

const REGISTERED = [
  { name: 'Bun version', fn: checkBun },
  { name: 'DB schema',   fn: checkDb },
  { name: 'Ollama',      fn: checkOllama },
  { name: 'Reranker',    fn: checkReranker },
  { name: 'CC hooks',    fn: checkHooks },
  { name: 'Angel',       fn: checkAngel },
];

async function main(): Promise<number> {
  const wantJson = process.argv.includes('--json');

  const report = await runChecks(REGISTERED);

  if (wantJson) {
    process.stdout.write(formatJson(report) + '\n');
  } else {
    process.stdout.write(formatHuman(report) + '\n');
  }

  return report.overall === 'pass' ? 0 : 1;
}

main()
  .then((code) => process.exit(code))
  .catch((err) => {
    process.stderr.write(`doctor crashed: ${(err as Error).stack ?? err}\n`);
    process.exit(2);
  });
```

Notes:
- The registered name in `REGISTERED` is informational for the runner only — each `CheckFn` returns its own `name` field which is what ends up in the report. Keeping the registry-name aligned with the CheckResult name is conventional but not enforced.
- Order matters for the human table: Bun first (foundation), DB second (structural), then network checks (Ollama, Reranker), then install-state checks (hooks, Angel). The CONTEXT.md sample output suggests this order.
- `--json` is detected with `process.argv.includes('--json')` — no full argv parser needed for one flag.
- The catch-all at the bottom is the DIAG-08 exit-2 contract: any uncaught exception → stderr trace + exit 2.
</task>

<task id="05-tests-doctor-cli">
**Create `src/tests/cli/doctor.test.ts`** — doctor orchestrator integration test (≥3).

Use `child_process.spawnSync` to invoke `dist/cli/doctor.cjs` (after `bun run build`). For a unit-style approach without a build step, instead import `runChecks` and exercise the formatter+exit-code logic directly.

Recommended approach: extract the orchestration logic from `main()` into a testable function:

```ts
// src/cli/doctor.ts (refactor)
export async function runDoctor(opts: { json: boolean }): Promise<{ exitCode: number; output: string }> {
  const report = await runChecks(REGISTERED);
  const output = opts.json ? formatJson(report) : formatHuman(report);
  return { exitCode: report.overall === 'pass' ? 0 : 1, output };
}

async function main(): Promise<number> {
  const wantJson = process.argv.includes('--json');
  const { exitCode, output } = await runDoctor({ json: wantJson });
  process.stdout.write(output + '\n');
  return exitCode;
}
```

Tests against `runDoctor`:

1. **Live pass run on this dev box**: just call `runDoctor({ json: false })`. Since the dev environment IS healthy (per CONTEXT.md acceptance #1), expect `exitCode === 0`. This is a smoke test — it proves the orchestrator wires correctly. (If this is too flaky, gate it behind a `process.env.LIVE_DOCTOR === '1'` flag.)
2. **--json produces valid JSON**: `runDoctor({ json: true })` → `JSON.parse(output)` doesn't throw; result has `status`, `checks`, `startedAt`, `durationMs`.
3. **Mocked failure → exit 1**: Mock one of the imported checks (e.g., `vi.mock('../../src/diagnostics/check-db.js', () => ({ checkDb: async () => ({ name: 'DB schema', status: 'fail', detail: 'forced', remediation: 'test' }) }))`). Assert `exitCode === 1`.

If the implementer prefers a true subprocess test, run `node dist/cli/doctor.cjs --json` post-build, parse stdout, assert exit code and JSON shape. Either approach satisfies CONTEXT.md acceptance #5.

## Notes for the implementer

- The `runDoctor` extraction (task 05) is optional but strongly recommended — testing `main()` directly is awkward because of `process.exit` calls. A pure function that returns `{ exitCode, output }` is much cleaner.
- If `bun run doctor` reports a fail on this dev box (despite CONTEXT.md asserting v4 is healthy), DON'T fix the symptom in doctor — investigate the actual install issue and report back. Doctor is supposed to be honest.
- The exit-2 contract matters: an uncaught exception in any check shouldn't reach the catch-all because the runner traps per-check errors. Exit 2 is reserved for failures of the orchestrator itself (e.g., `runChecks` throws — which it shouldn't, but defense-in-depth).
- Don't add a `--verbose` flag, a `--check <name>` flag, a `--quiet` flag, or any other UX feature beyond `--json`. CONTEXT.md plan_authorization scope is `--json` only.
