# Plan 15-01: Diagnostic primitives

## Objective

Build the framework that every Phase 15 diagnostic check plugs into: a single `CheckResult` shape, a parallel `runChecks` runner that aggregates results and traps per-check exceptions, and the directory layout under `src/diagnostics/`. No actual checks are implemented in this plan — those land in 15-02..15-04. This plan exists so the per-check plans can run in parallel against a stable contract.

## Why this comes first

The CONTEXT.md decision section locks the `CheckResult` shape and the runner's parallel/aggregate behavior. Without the shape and runner committed, the three downstream plans (15-02 Bun+DB, 15-03 Ollama+Reranker, 15-04 Hooks+Angel) can't be authored against a stable interface, and import paths drift. Putting it in Wave 1 also lets the Wave 2 plans run in parallel without coordinating on type definitions.

## Tasks

<task id="01-types">
**Create `src/diagnostics/types.ts`** — the shared contract.

```ts
export type CheckStatus = 'pass' | 'fail' | 'warn';

export interface CheckResult {
  name: string;          // 'Bun version', 'Ollama', etc.
  status: CheckStatus;
  detail: string;        // human-readable one-liner ('Bun 1.3.5', 'Bun not found')
  remediation?: string;  // populated only when status !== 'pass'
  durationMs: number;    // wall-clock duration of the check, set by runner
}

export type CheckFn = () => Promise<Omit<CheckResult, 'durationMs'>>;

export interface RegisteredCheck {
  name: string;
  fn: CheckFn;
}

export type OverallStatus = 'pass' | 'fail';  // warn alone does not fail the run

export interface DoctorReport {
  overall: OverallStatus;
  checks: CheckResult[];
  startedAt: string;     // ISO timestamp
  durationMs: number;    // total wall-clock duration of all checks (parallel — not sum)
}
```

Notes:
- `CheckFn` returns the result *minus* `durationMs` so the runner is the sole authority for timing (one place to change later if we ever want a stopwatch helper).
- `OverallStatus` deliberately excludes `'warn'` — per CONTEXT.md, warn does not fail the run; warns surface in individual `CheckResult.status` only.
- No I/O in this file. Pure types.
</task>

<task id="02-runner">
**Create `src/diagnostics/runner.ts`** — the parallel aggregator.

Required exports:

```ts
export async function runChecks(checks: RegisteredCheck[]): Promise<DoctorReport>;
```

Behavior:
1. Record `startedAt = new Date().toISOString()` and a `runStart = performance.now()`.
2. For each registered check, build a wrapped promise that:
   - Records `t0 = performance.now()` immediately before invoking the check function.
   - Awaits the check function inside a `try`/`catch`.
   - On success, returns `{ ...result, durationMs: Math.round(performance.now() - t0) }`.
   - On thrown error, returns a synthetic `CheckResult` with `status: 'fail'`, `name: registered.name`, `detail: 'check threw: ' + (err.message ?? String(err))`, `remediation: 'Check src/diagnostics/<file>.ts logs and re-run with stderr capture.'`, and a measured `durationMs`.
3. `await Promise.all(...)` — checks run concurrently. The CONTEXT.md sample output is sub-second per check, but this matters for UX: total wall-clock is `max(durationMs)`, not the sum.
4. Compute `overall`: if any `result.status === 'fail'` → `'fail'`; otherwise `'pass'`. Warn-only and pass-only both yield `'pass'`.
5. Return the aggregated `DoctorReport`.

Hard requirements:
- Never let one broken check take the whole doctor down. The try/catch around each `fn()` call is mandatory.
- `runChecks` must NOT print anything. It returns data; printing is the CLI's job (PLAN-15-05).
- No process.exit, no global side effects. Pure function of its input.
</task>

<task id="03-tests">
**Create `src/tests/diagnostics/runner.test.ts`** — runner unit tests.

Use vitest (the project's `bun run test` runner). Mock checks are hand-written async functions; no module mocks needed.

Required test cases (≥3):

1. `runChecks() with all-pass checks → overall 'pass'`
   - Build two synthetic `RegisteredCheck`s whose functions return `{ name, status: 'pass', detail: 'ok' }`.
   - Assert `report.overall === 'pass'`, both results present in order, both have `durationMs >= 0`.

2. `runChecks() with one fail and one pass → overall 'fail'`
   - One synthetic check returns `status: 'pass'`, the other `status: 'fail'` with `remediation: '...'`.
   - Assert `report.overall === 'fail'` and the failing remediation is preserved.

3. `runChecks() traps thrown errors → coerces to fail`
   - One synthetic check throws `new Error('boom')`.
   - Assert that check's `result.status === 'fail'`, `result.detail.includes('boom')`, and the OTHER check still ran (parallel, not short-circuit).
   - Assert `report.overall === 'fail'`.

Optional 4th test if cheap to add:

4. `runChecks() with only warns → overall 'pass'`
   - Two synthetic checks both return `status: 'warn'`.
   - Assert `report.overall === 'pass'` (per CONTEXT.md: warn is not fail).

Naming: test file lives at `src/tests/diagnostics/runner.test.ts` to match the existing `src/tests/cli/*.test.ts` convention. Create the `src/tests/diagnostics/` directory.
</task>

## Notes for the implementer

- Don't be tempted to inline a "default exports list" of checks in `runner.ts`. Keep `runChecks` agnostic — the registry of which checks to run lives in the CLI orchestrator (PLAN-15-05). This keeps tests simple and lets future checks plug in without touching the runner.
- `performance.now()` is available in Node 22+ globally; no import needed.
- The synthetic-error test message format is asserted loosely (`detail.includes('boom')`) so a future tweak to the error coercion message doesn't break the test.
