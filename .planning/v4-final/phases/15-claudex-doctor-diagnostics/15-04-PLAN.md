# Plan 15-04: Hooks + Angel checks (DIAG-06, DIAG-07)

## Objective

Implement the two diagnostic checks that read installed Claudex state on the local filesystem rather than probing services: CC hooks registration (DIAG-06) and Angel process liveness + heartbeat freshness (DIAG-07).

DIAG-07 has a wrinkle that justifies a focused plan: CONTEXT.md says "query the telemetry table for the most recent heartbeat row" but the telemetry table's `event_kind` CHECK constraint does NOT permit a `'heartbeat'` value, and the hard-gate forbids schema migrations. The plan resolves this with a zero-schema-change signal: heartbeat freshness is encoded as the **mtime of the PID file**, refreshed by `heartbeatTick` on each successful tick.

## Why these are grouped

Both checks read local Claudex install state without network probes. They share zero code with the Bun/DB plan (15-02) and zero code with the Ollama/reranker plan (15-03). Grouping them lets one implementer cover the install-correctness surface end-to-end.

<task id="02-check-hooks">
**Create `src/diagnostics/check-hooks.ts`** — DIAG-06.

```ts
import * as fs from 'fs';
import type { CheckFn } from './types.js';
import { getSettingsJsonPath, EXPECTED_HOOK_NAMES } from '../cli/setup.js';

export const checkHooks: CheckFn = async () => {
  const settingsPath = getSettingsJsonPath();

  if (!fs.existsSync(settingsPath)) {
    return {
      name: 'CC hooks',
      status: 'fail',
      detail: `${settingsPath} not found`,
      remediation: "Claude Code settings missing. Run 'bun run setup' to register hooks.",
    };
  }

  let parsed: { hooks?: Record<string, Array<{ hooks?: Array<{ command?: string }> }>> };
  try {
    parsed = JSON.parse(fs.readFileSync(settingsPath, 'utf-8'));
  } catch (err) {
    return {
      name: 'CC hooks',
      status: 'fail',
      detail: `settings.json malformed: ${(err as Error).message}`,
      remediation: 'Fix or restore ~/.claude/settings.json then run bun run setup.',
    };
  }

  const hooks = parsed.hooks ?? {};
  const found: string[] = [];
  const missing: string[] = [];

  for (const name of EXPECTED_HOOK_NAMES) {
    const entries = Array.isArray(hooks[name]) ? hooks[name] : [];
    const hasClaudex = entries.some((entry) =>
      Array.isArray(entry.hooks) &&
      entry.hooks.some((h) => typeof h.command === 'string' && h.command.toLowerCase().includes('claudex'))
    );
    if (hasClaudex) found.push(name);
    else missing.push(name);
  }

  if (missing.length === 0) {
    return {
      name: 'CC hooks',
      status: 'pass',
      detail: `${found.length} of ${EXPECTED_HOOK_NAMES.length} registered`,
    };
  }

  return {
    name: 'CC hooks',
    status: 'fail',
    detail: `${found.length} of ${EXPECTED_HOOK_NAMES.length} registered (missing: ${missing.slice(0, 3).join(', ')}${missing.length > 3 ? `, +${missing.length - 3} more` : ''})`,
    remediation: "Hooks not registered. Run 'bun run setup' to patch ~/.claude/settings.json.",
  };
};
```

Notes:
- The "is Claudex" detection mirrors `setup.ts` `patchSettingsJson` (line 126-133): a hook entry is considered Claudex's if its `command` string contains `'claudex'` (case-insensitive). This catches both legacy `CLAUDEXv3` paths and current `claudex` paths.
- Only the COUNT and missing-list are asserted; we don't validate the exact path inside each command (that would couple doctor to install location). Phase 14's `bun run setup --verify` (if it exists) is the authoritative path-validator; doctor stays at "is the entry there at all."
- Truncate the missing list to 3 items + "+N more" so the detail line stays terminal-friendly. Full list is recoverable via `--json`.
</task>

<task id="03-heartbeat-pid-touch">
**Add PID-file mtime touch in `src/angel/heartbeat.ts`.**

The doctor's freshness signal is the PID file mtime. For that to be meaningful, the heartbeat must update it on every successful tick.

Where to add: the bottom of `heartbeatTick` in `src/angel/heartbeat.ts`, inside the success path (i.e., AFTER the work for the tick has completed but BEFORE the function returns the `TickResult`). Use a try/catch — failure to touch the PID file must NOT break the heartbeat.

```ts
// at the top of the file (or near other imports)
import * as fs from 'fs';
// (getPidFilePath already lives in src/angel/index.ts; import it OR pass through ctx)

// Inside heartbeatTick, after successful work:
try {
  const pidPath = getPidFilePath();  // imported from index.js
  const now = new Date();
  fs.utimesSync(pidPath, now, now);
} catch (err) {
  // Non-critical — failing to refresh PID mtime shouldn't kill the heartbeat
  log('warn', 'pid file mtime touch failed', { err: String(err) });
}
```

Implementation note: `getPidFilePath` currently lives in `src/angel/index.ts` as an internal function. Promote it to an export (single-line change):

```ts
// src/angel/index.ts
export function getPidFilePath(): string { ... }  // already exists; just add 'export'
```

Why mtime, not telemetry: CONTEXT.md hard-gates "DB schema unchanged (no migrations)". The `telemetry.event_kind` CHECK constraint excludes `'heartbeat'`. Adding it would require a migration, which is forbidden. PID-file mtime is a zero-schema-change signal that has the additional benefit of being a single atomic FS call — no DB lock contention with consolidator/sweep code paths.

Acceptable alternative: re-use an existing `event_kind` (e.g., `'observation_capture'`) — but this distorts telemetry semantics and pollutes pre-existing histograms. PID mtime is cleaner.
</task>

<task id="04-check-angel">
**Create `src/diagnostics/check-angel.ts`** — DIAG-07.

```ts
import * as fs from 'fs';
import type { CheckFn } from './types.js';
import { getPidFilePath } from '../angel/index.js';

const HEARTBEAT_FRESHNESS_MS = 60_000;

export const checkAngel: CheckFn = async () => {
  const pidPath = getPidFilePath();

  if (!fs.existsSync(pidPath)) {
    return {
      name: 'Angel',
      status: 'fail',
      detail: 'no PID file',
      remediation: "Angel not running. Open Claude Code (auto-spawns Angel via session-start hook) or run 'node dist/angel/index.cjs'.",
    };
  }

  const pidStr = fs.readFileSync(pidPath, 'utf-8').trim();
  const pid = parseInt(pidStr, 10);
  if (isNaN(pid)) {
    return {
      name: 'Angel',
      status: 'fail',
      detail: `PID file contains non-numeric value: '${pidStr}'`,
      remediation: `Delete ${pidPath} and restart Angel via Claude Code session-start.`,
    };
  }

  try {
    process.kill(pid, 0);  // signal 0 = existence check, doesn't kill
  } catch {
    return {
      name: 'Angel',
      status: 'fail',
      detail: `PID ${pid} not running (stale PID file)`,
      remediation: `Delete ${pidPath} and restart Angel via Claude Code session-start.`,
    };
  }

  // Heartbeat freshness — PID file mtime is touched by heartbeatTick.
  const stat = fs.statSync(pidPath);
  const ageMs = Date.now() - stat.mtimeMs;

  if (ageMs >= HEARTBEAT_FRESHNESS_MS) {
    return {
      name: 'Angel',
      status: 'warn',
      detail: `PID ${pid} alive but last heartbeat ${Math.round(ageMs / 1000)}s ago (>=60s)`,
      remediation: 'Angel may be stuck in a long consolidation cycle. If this persists, restart via Claude Code session-end + session-start.',
    };
  }

  return {
    name: 'Angel',
    status: 'pass',
    detail: `PID ${pid}, heartbeat fresh (${Math.round(ageMs / 1000)}s)`,
  };
};
```

Notes:
- Cross-platform: `process.kill(pid, 0)` works on both Windows and Unix as a process-existence probe. EPERM is treated as "process exists, just not ours" — but for a self-spawned Angel that never happens. Treat any thrown error as "process gone."
- Stale heartbeat = `warn` (not fail). CONTEXT.md is explicit: Angel can be busy in a long consolidation cycle and that's not a fail condition.
- `HEARTBEAT_FRESHNESS_MS = 60_000` matches CONTEXT.md "<60s".
- We deliberately do NOT call any Angel API (no `getAngelStatus()` or similar) — doctor is read-only and must work even if Angel is dead.
</task>

<task id="06-tests-angel">
**Create `src/tests/diagnostics/check-angel.test.ts`** — ≥3 tests.

Mock pattern: write a temp PID file, mock `getPidFilePath`. For PID-existence, use `process.pid` (the test process itself) as a known-alive PID; use a known-dead PID for the stale case (large numeric like `999999` is risky on Windows; better to spawn-and-kill a child or write `'1'` and treat the resulting EPERM as "alive elsewhere" — actually the cleanest is `process.pid` for alive, and an unallocated pid for dead. Vitest gives us `process.pid`; for dead, use the helper `findUnusedPid()` we write inline).

Required cases:

1. **pass (alive + fresh)**: write PID file with `process.pid`; run check immediately → `'pass'`, detail mentions `'fresh'`.
2. **fail (no PID file)**: point at non-existent path → `'fail'`, detail `'no PID file'`.
3. **fail (PID dead)**: write a PID file with an obviously-dead PID. The simplest cross-platform approach: spawn a `child_process.spawn` with `{ stdio: 'ignore' }`, capture its PID, kill it, wait for it to exit, then write its now-stale PID to the file. Run check → `'fail'`, detail mentions `'stale PID'`.
4. **warn (heartbeat stale)**: write PID file with `process.pid`, then `fs.utimesSync` the file to a timestamp 90 seconds in the past. Run check → `'warn'`, detail mentions `'>=60s'`.
5. (optional) **fail (PID file non-numeric)**: write `'not-a-pid'` → `'fail'`, detail mentions `'non-numeric'`.

Total: 4-5 tests for DIAG-07.

Note for the implementer: the dead-PID test is the trickiest. If spawning a child process is too flaky in CI, an acceptable alternative is to mock `process.kill` via `vi.spyOn(process, 'kill').mockImplementation(() => { throw new Error('ESRCH'); })` for that one test and assert the result.
</task>
