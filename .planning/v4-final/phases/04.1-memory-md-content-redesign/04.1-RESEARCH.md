## Summary

Phase 4.1 has TWO bug fixes with concrete code targets, ONE schema migration, and ONE substrate build (lesson files + curation pipeline + bridge to `critical_rules`).

**Bug #1 — Writer state-machine corruption (CUR-13).** Visible at `~/.claude/projects/.../CLAUDEXv3/memory/MEMORY.md` line 38: `<!-- USER EDITABLE -->\` marker present, \`## User Notes\` below`. This is *literal text from a previous user-tail body* that contained the marker as a substring (not as a real boundary marker). The bug is at `memory-md-writer.ts:580`: `markerIdx = existing.indexOf('<!-- USER EDITABLE -->')` — `indexOf` matches the marker as a *substring* anywhere in the file, including inside body text that happens to mention the marker. When that match is *before* the real marker line, the user-tail extraction starts mid-body and includes a duplicated `## How to Query` block. **Fix:** match the marker only when it sits on its own line (e.g., regex `/^<!-- USER EDITABLE -->$/m` returning the byte offset of the line start, NOT the substring offset).

**Bug #2 — `transcript_chunk` timestamp precision (CUR-14).** `transcript-chunker.ts:333` extracts `lastTs = segTurns[segTurns.length - 1].timestamp_epoch`. `conversation_turns.timestamp_epoch` stores `unixepoch()` (seconds, 10-digit). The `INSERT INTO artifact(...created_at_epoch...)` at line 318 then writes that 10-digit-seconds value, while peer artifact kinds write `Date.now()` (13-digit ms). This breaks recency-weighted retrieval ordering (a transcript_chunk from 1 hour ago looks 1000× older than a `mental_model` from 1 hour ago). **Fix:** multiply by 1000 at write time. Also add the read-time normalization helper (`epoch_ms = value < 1e12 ? value * 1000 : value`) for the existing 20 rows that already have second-precision values.

**Schema migration (V18).** Two changes:
1. `critical_rules` needs `multi_project_count INTEGER DEFAULT 1`. Under V17, `critical_rules` is a *view* over `artifact` where `kind='critical_rule'`, with the row payload in JSON `data`. Two paths:
   - **(a)** Store `multi_project_count` inside `data` JSON; access via `json_extract(data, '$.multi_project_count')`. No DDL change needed. Scoring boost in `critical-reminders.ts` reads from extra column on the SELECT.
   - **(b)** Add a real column to the underlying `artifact` table or extend the view with a join to a sidecar table.
   Recommend **(a)** — simpler, V17-compatible, no view-rewrite, matches existing pattern (`json_extract(data, '$.source')` is already used in v17-ddl.ts:139).
2. Two new tables: `shape_vocabulary` (canonical) + `shape_candidates` (pending). These are NEW tables, not legacy-view-over-artifact. Use `CREATE TABLE IF NOT EXISTS` in a new `migrateV17toV18` step + bump `TARGET_VERSION` to 18.

**Substrate build.** New lesson-file writer (`src/angel/lesson-writer.ts`?), new heartbeat sweeps for: feedback density check + multi_project_count update + shape vocabulary promotion. New `## Lessons` section in `memory-md-writer.ts`; remove `renderEntities` and `renderRecentThreads` from the assembly. New `/endsession` proposal flow.

**Primary recommendation:** Decompose into 9 plans across 4 waves. Wave 1 = schema (V18 migration) + read-time normalization helper. Wave 2 = writer bug fix + transcript-chunker bug fix (both block clean live-fire). Wave 3 = lesson-file writer + MEMORY.md section restructure (Lessons section + drop Entities/Threads). Wave 4 = Angel heartbeat sweeps (feedback density → critical_rules; multi_project_count update; shape vocabulary promotion) + scoring boost in critical-reminders.ts. Plus 2 plans for `/endsession` curation flow and behavioral live-fire test harness.

## Architecture Patterns

### Pattern 1: Idempotent writer with sentinel + atomic rename
Already implemented in `memory-md-writer.ts:609-628`. Pattern: write to `<path>.tmp`, `fs.renameSync` to target, retry once on Windows lock race (busy-wait 50ms). Lesson-file writer should follow this pattern.

### Pattern 2: V17 view + JSON sidecar for new fields
Per `v17-ddl.ts:138-143`: indexes use `json_extract(data, '$.field')` against the `artifact` table. New fields on legacy entities go into `data` JSON, accessed via `json_extract`. Avoids view-rewrites. Pattern applies to `multi_project_count`.

### Pattern 3: Heartbeat sweep with iteration-level + per-operation try/catch
Per `heartbeat.ts:417-433` (Plan 04-06-02 lessons): outer try/catch protects against DB errors; inner try/catches wrap each risky call so one bad row doesn't kill the loop. Apply to all three new sweeps.

### Pattern 4: Deferred applyEffects for scorer side effects
Per `critical-reminders.ts:432-449`: scorer returns `{ section, applyEffects }` so callers can decide when to commit injection counters. Lesson Tier scoring (DEFERRED to 6.5) should match this pattern. 4.1 only extends the existing rule scorer.

### Pattern 5: SAFETY_KEYWORDS regex for drift_risk inference
Per `critical-reminders.ts:146`: `/\b(never|deadlock|scope|verify|safety)\b/i`. Reuse for feedback bridge inference per CONTEXT.md decision.

### Anti-patterns to avoid

- **DON'T `indexOf` for line-anchored markers.** Use `split('\n')` + equality check or `^...$` regex with `m` flag. The CUR-13 bug exists because of `indexOf`.
- **DON'T do data migration for the timestamp bug.** Per CONTEXT.md: read-time normalization only. Touching 20 rows is cheap but the principle is "no data migration; read-time normalization is reversible."
- **DON'T add Experience Tier scoring in 4.1.** That's Phase 6.5. 4.1 ships substrate (lesson files + bridge) only. Do NOT write a scorer for `project_*` and `process_*`.
- **DON'T edit reranker.** 4.1 does not touch the reranker pipeline.
- **DON'T conflate `feedback_*` density check with `promoteFromCapabilityTracker`.** Different triggers (LLM-extracted `feedback_*` vs capability_tracker correction rate). Same downstream insert.
- **DON'T cap foreground lessons at a hard count BELOW 20 unless budget pressure.** Per CONTEXT.md: "no hard count cap — foreground is bounded by attention budget, not entry count." Default 20, tunable.

## Common Pitfalls

### Pitfall 1: Multi-project_count flicker on new project onboarding
**What goes wrong:** A user gives the same feedback in project A 3 times. It promotes locally. Multi_project_count=1. User starts working on project B; gives the same feedback once. Heartbeat counts: 1 project (A) has 3 hits, project B has 1 hit. `multi_project_count=1` (NOT 2 — project B hasn't promoted locally yet). Boost doesn't fire until project B independently reaches density 3.
**How to avoid:** Per CONTEXT.md, this is *intentional* — cross-project escalation without local density is Phase 6.5. Don't try to fix it in 4.1; document the expected behavior.
**Warning signs:** Bug reports of "I've said this same thing in 3 projects, why isn't it boosted?" — answer: each project must reach local density 3 first.

### Pitfall 2: Foreground-tier rotation creating noise during demotion
**What goes wrong:** Lesson hasn't fired in 7 weeks, 6 days. Promotion check at 8 weeks demotes it. User comments "where did that lesson go?" Lesson is still on disk in background tier, but feels lost.
**How to avoid:** Demotion is reversible — next firing re-promotes to foreground. Document this in `## How to Query` static text or in the lesson-file frontmatter's `tier_history` field.

### Pitfall 3: Heartbeat enumeration thrashing for inactive projects
**What goes wrong:** Heartbeat sweep enumerates ALL active projects every tick. On a busy machine with 10+ projects, each `curateMemoryMd` call reads disk, hashes, compares. Even with idempotent fast-path, that's 10× disk reads per heartbeat tick (default cadence 60s).
**How to avoid:** Run cross-project enumeration on a *slower* cadence (e.g., every 5 ticks) tracked via Angel `last_*_at` checkpoints. Or use `memory_curation_pending` events as the trigger — the existing path. Per-project re-curation only when something changed.
**Warning signs:** Heartbeat duration_ms > 5000 on machines with many projects.

### Pitfall 4: User-authored MEMORY.md migration loss on first sentinel-write
**What goes wrong:** Lacuna-Betting has 50 lines of carefully-curated user-authored MEMORY.md with no sentinel. Phase 4.1 writer runs: detects no sentinel, currently *refuses* (`sentinel_missing`). Plan must add the wrap-existing-content path, but if logic is wrong, Lacuna's content gets clobbered.
**How to avoid:** First-run migration MUST be tested against synthetic Lacuna/Oracle/Nexus fixtures BEFORE running on real user files. Add a `--dry-run` flag to the writer that returns the planned output without writing. Test in CI.
**Warning signs:** User reports "my MEMORY.md got eaten." Catastrophic. Must not happen.

### Pitfall 5: `process_*` salience triggers firing too often
**What goes wrong:** 2-of-5 trigger seems conservative but if a session has both ≥2 corrections AND a long-form discussion, it fires. If many sessions have those properties, every session writes a `process_*` lesson. Files multiply, MEMORY.md `## Lessons` section grows, foreground cap kicks in, demotion churn rises.
**How to avoid:** Max 1 `process_*` per session is locked. But enforce it strictly — don't allow override flag to bypass the cap. Monitor `process_*` write rate in 4.1 soak; if >1 per 3 sessions on average, threshold needs tuning (Claude's discretion per CONTEXT.md).

### Pitfall 6: V17 view rewrite blocking V18 migration
**What goes wrong:** Adding `multi_project_count` as a real column to `critical_rules` means rewriting the V17 view + the INSTEAD OF triggers. That's hours of risk. The JSON-in-data path avoids it but means scorer SQL has `json_extract` overhead.
**How to avoid:** Use JSON-in-data path. Benchmark: `json_extract` on indexed JSON is ~1 µs per row; with 50 rules per project, total scoring overhead is <1 ms. Acceptable.

### Density-3 SQL for feedback bridge (Claude's discretion area)
```sql
-- Find feedback rule_texts with ≥3 instances in this project
SELECT
  lower(replace(replace(replace(trim(body), '.', ''), ',', ''), '!', '')) AS norm_text,
  COUNT(DISTINCT session_id) AS sess_count,
  MIN(created_at_epoch) AS earliest_epoch
FROM artifact
WHERE kind = 'lesson'
  AND project_id = ?
  AND json_extract(data, '$.type') = 'feedback'
GROUP BY norm_text
HAVING sess_count >= 3
   AND NOT EXISTS (
     SELECT 1 FROM artifact cr
     WHERE cr.kind = 'critical_rule'
       AND cr.project_id = ?
       AND lower(cr.body) = norm_text
       AND json_extract(cr.data, '$.source') = 'system-promoted'
   )
ORDER BY sess_count DESC
LIMIT 10;
```

### Multi-project count update (cross-project sweep)
```sql
-- For each system-promoted critical_rule, count distinct projects with similar text
WITH norm_rules AS (
  SELECT
    id, project_id,
    lower(replace(replace(replace(trim(body), '.', ''), ',', ''), '!', '')) AS norm_text
  FROM artifact
  WHERE kind = 'critical_rule'
    AND json_extract(data, '$.source') = 'system-promoted'
)
SELECT
  r.id,
  (SELECT COUNT(DISTINCT n.project_id) FROM norm_rules n WHERE n.norm_text = r.norm_text) AS multi_count
FROM norm_rules r;
```
