<objective>
Produce an exhaustive, classified audit of hardcoded path separators and platform-specific path constructions in `src/` for PLAT-01. The output is a findings file at `.planning/phases/13-cross-platform-code-audit/13-01-AUDIT-PATHS.md` that 13-04 (fix execution) consumes to apply fixes.

This plan is read-only — no source files are modified. The deliverable is the audit document.

CONTEXT.md `<decisions>` lines 40-53 lock the audit method (3-pass grep) and the acceptable-to-keep patterns (URL paths, regex, opaque IDs, test fixtures, intentional `path.win32` usage). Use that as the classification rubric — do not invent new categories.
</objective>

<execution_context>
**What "hardcoded `\\` separator" means in this codebase:**
- A literal `'\\'` or `"\\"` inside a string used to construct a filesystem path (e.g., `dir + '\\' + file`)
- A regex `\\\\` pattern that matches Windows-only path separators in code that runs on user paths (not in code that intentionally tests Windows behavior)
- A template literal `${dir}\\${file}` building a filesystem path

**What's acceptable to keep (per CONTEXT.md):**
- URL paths — forward slashes in HTTP/MCP URLs
- Internal opaque identifiers that look like paths but aren't filesystem paths (e.g., scoring keys in `claudex_search`)
- Regex patterns that match POSIX-style paths in handoff bodies (the `parseHandoffHeader` family)
- Test fixtures that test platform-specific normalization (e.g., a test asserting `path.win32.normalize` produces a backslash result)
- Comments / docstrings that document Windows quirks

**Audit method (CONTEXT.md `<decisions>` PLAT-01):**
- Pass 1 — `grep -rn` for hardcoded backslashes in string literals across `src/`
- Pass 2 — Audit `path.normalize`, `path.win32`, `path.posix` callsites in `src/` to confirm they're intentional, not workarounds for missing `path.join`
- Pass 3 — Inspect string concatenation that builds paths (e.g., `dir + '\\' + file`, template literals with `\\`)

**Out of scope here:**
- `services/reranker.py` (Python, separate concern)
- `node_modules/`, `dist/`, `.git/`
- `.planning/`, `context/`, `.claude/`, `docs/`, `README.md` — these are docs, not code
- `tests/` fixtures that intentionally exercise Windows behavior — keep them, document the rationale

**Deliverable shape:**
A markdown table with one row per grep hit, sorted by file. Columns: `file:line`, `current_code` (one-line excerpt), `classification` (`fix-needed` / `keep`), `reason_or_replacement`. Plus a header noting the grep commands used and the totals (e.g., "47 hits total → 38 fix-needed → 9 keep").

The fix-needed entries are the consumable input for 13-04. The keep entries are documented so the phase-close audit (acceptance criterion 1 in CONTEXT.md) can confirm zero unjustified hits remain.
</execution_context>

Classification rubric (apply per CONTEXT.md `<decisions>` PLAT-01):
- **keep** if the hit is: a URL path, an opaque internal ID, a regex pattern matching POSIX paths in handoff bodies, a test fixture for Windows-specific normalization, a comment / docstring documenting Windows quirks
- **fix-needed** otherwise

For each fix-needed row, propose the concrete replacement that 13-04 will apply:
- `dir + '\\' + file` → `path.join(dir, file)`
- `__dirname + '\\..\\config.json'` → `path.resolve(__dirname, '..', 'config.json')`
- A `path.normalize(...)` workaround → `path.join(...)` directly
- A regex `\\\\` for matching paths in code that processes user paths → `[\\\\/]` or use `path.sep` if the regex is built dynamically
