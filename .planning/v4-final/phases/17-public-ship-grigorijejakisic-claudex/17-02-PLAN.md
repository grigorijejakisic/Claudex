# Plan 17-02: v4.1.0 annotated tag + push to public

## Objective

Create the `v4.1.0` annotated tag at the commit Plan 17-01 produced, then push the complete master history (336 commits ahead of `public/master` + 17-01's commit = 337 commits) and both tags (`v4.0.0` + `v4.1.0`) to `git@github.com:grigorijejakisic/Claudex.git`.

This is the irreversible-ish step. Once `master` lands publicly on `grigorijejakisic/Claudex`, the repo is visible to strangers — clones can begin, search engines can index. CONTEXT.md `<open_questions>` flags this as the "initial visibility moment is one-shot."

Closes REL-02 (push history + tags) and REL-03 (v4.1.0 annotated tag).

## Why this comes second

CONTEXT.md `<decisions>` "CHANGELOG.md update for v4.1.0" sequence: "CHANGELOG update → commit → tag → push." Plan 17-01 produced the commit; this plan creates the tag at that commit and pushes. Putting tag creation here (not in 17-01) keeps the commit atomic — the commit is "CHANGELOG promote + badges," and the tag is metadata pointing at that commit, not part of the commit's content.

Also: keeping push separate from CHANGELOG/badges authoring means a regression in any local check (gates, badge URL typo) is recoverable with a `git commit --amend` to 17-01's commit, **before** the tag is created. Once the tag exists at a hash, amending becomes a destructive operation.

```bash

# Public/master HEAD matches expected baseline

# Expected: 712c910... (matches CONTEXT.md acceptance criterion #1)

# v4.0.0 tag exists locally
git tag --list 'v4.0.0'
# Expected: v4.0.0

# v4.1.0 tag does NOT yet exist locally
git tag --list 'v4.1.0'
# Expected: (empty)

# Hard gates green at this hash
bun run build
bun run test

```

If any of these checks fail, **stop and SendMessage team-lead** describing what failed. Do NOT proceed to tag creation. Common recoverables (handle in this plan):

- `git status` shows untracked files that should have been committed in 17-01 → amend 17-01's commit (still safe, no tag yet) and re-run pre-flight
- `git log` shows HEAD is not Plan 17-01's commit → 17-01 did not land, escalate to team-lead

Common non-recoverables (escalate, do not fix in this plan):

- `git merge-base --is-ancestor public/master master` returns false → would mean a non-fast-forward push is needed; CONTEXT.md `<plan_authorization>` explicitly forbids force-push; HALT and SendMessage team-lead
- `bun run vesna` fails → behavioral regression; HALT
- Public remote URL has changed → escalate

<task id="03-push-master-to-public">
**Push `master` to `public` as fast-forward.** This is the irreversible-ish moment.

```bash
git push public master
```

**Expected output (success):**

```
Enumerating objects: <N>, done.
...
To git@github.com:grigorijejakisic/Claudex.git
   712c910..<new_HEAD>  master -> master
```

**The leading commit hash MUST be `712c910`** — that confirms fast-forward. If the output shows a different starting hash, something has drifted; HALT and SendMessage team-lead.

**Failure modes and responses:**

- `Permission denied (publickey)` → SSH key not registered for grigorijejakisic on this machine. SendMessage team-lead with the exact error; do NOT switch remote URL or retry; HALT.
- `! [rejected]        master -> master (non-fast-forward)` → public/master has advanced since planning (someone else pushed); SendMessage team-lead; do NOT use `--force`; HALT.
- `fatal: unable to access 'git@github.com:grigorijejakisic/Claudex.git/'` → network error or remote URL changed; SendMessage team-lead; HALT.

**Verify after push:**

```bash
git ls-remote public refs/heads/master
# Expected: <local HEAD hash>  refs/heads/master
```

The local HEAD hash from `git rev-parse HEAD` MUST match the hash returned by `ls-remote`. If they differ, the push didn't land on master (somehow ended up on a different ref); HALT and SendMessage team-lead.
</task>

<task id="04-push-tags-to-public">
**Push tags to `public`.** This sends `v4.0.0` (which was created by Phase 11 close at `f8f617c` but never pushed to `public`) and the freshly-created `v4.1.0`.

# Expected: <hash>  refs/tags/v4.0.0  (annotated tag → commit hash f8f617c, plus the tag object hash)

# Expected: <hash>  refs/tags/v4.1.0  (annotated tag → current HEAD's hash)
```

Both must resolve. If `v4.1.0` doesn't appear, retry with the explicit tag name:

```bash
git push public v4.1.0
```

If that also fails, HALT and SendMessage team-lead.

**Tag message verification on remote:**

```bash

Do NOT delete and re-create the remote tag (that would require force-push of a tag, an irreversible operation). Instead, SendMessage team-lead and accept the discrepancy as a known issue to address in a v4.1.1 patch.
</task>

## Notes for the implementer

- **Force-push is forbidden in this plan and the entire phase.** CONTEXT.md `<plan_authorization>` is explicit: "Force-push to public master (NOT NEEDED — fast-forward verified; if the situation changes and force-push is needed, escalate to operator)." If you encounter a non-fast-forward rejection, the correct response is SendMessage team-lead and HALT, not investigate-and-force.
- **gh CLI is NOT used in this plan.** The push uses native `git push`, which uses SSH (the `public` remote is `git@github.com:...`). `gh` CLI auth (Corleanus) is irrelevant at this step. Plan 17-03 is where gh's auth scope first matters (for `gh release create`).
- **Why the tag is at Plan 17-01's commit, not Plan 17-04's:** see Task 05's resolution. The tag points at content-complete v4.1.0 (CHANGELOG narrative + badges), not at planning admin (STATE updates). This matches the v4.0.0 precedent — v4.0.0 tag is at `f8f617c`, the v4.0.0 release-content commit, not at a subsequent phase-close commit.
- **The tag must precede the push.** `git push public master` followed by `git push public --tags` is two separate operations because pushing tags doesn't push the branch they live on (or vice versa). Both must run, in either order — but pre-creating the tag before the master push is conventional. The order Tasks 02 → 03 → 04 enforce is: create tag locally → push branch → push tags.
- **If the SSH push permission denial happens, the operator can run the push themselves.** Their machine has the SSH key registered. SendMessage team-lead with the exact error message; do NOT attempt workarounds (changing remote to HTTPS, using gh CLI, etc.) without explicit operator approval.
