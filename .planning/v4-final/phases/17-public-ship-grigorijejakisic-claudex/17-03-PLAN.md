# Plan 17-03: GitHub release + topics + branch protection runbook

## Objective

Apply three publication-layer artifacts on top of the public push from Plan 17-02:

1. **REL-04** — GitHub release object for `v4.1.0` at `github.com/grigorijejakisic/Claudex/releases/tag/v4.1.0`, with notes extracted from `CHANGELOG.md`'s `[4.1.0] — 2026-05-02` section
2. **REL-05** — repository topics on `grigorijejakisic/Claudex` (9 topics) for discoverability
3. **REL-07 (HITL)** — runbook at `docs/onboarding/branch-protection-setup.md` describing the GitHub UI click path for branch protection (operator runs the UI step post-ship; CONTEXT.md `<decisions>` "Branch protection (REL-07) — HITL" pattern)

Closes REL-04 + REL-05 fully; ships the runbook half of REL-07 (the UI click is operator-driven and remains HITL-pending until the operator runs it).

## Why this comes third

The release object and topics both reference state that only exists after Plan 17-02:

- `gh release create v4.1.0` requires the `v4.1.0` tag to exist on the remote
- `gh repo edit --add-topic ...` is for an existing public repo (the repo is already public, but the topics are a discoverability layer authored after the push)

The branch-protection runbook is the only piece that doesn't strictly require Plan 17-02 to land first, but bundling it here keeps Plan 17-04 (phase close) focused on STATE/ROADMAP admin.

## Operational risk: gh CLI auth scope

CONTEXT.md `<open_questions>` flagged this:

- The SSH `public` remote uses an SSH key (likely registered to `grigorijejakisic`) — Plan 17-02's push works.
- `gh` CLI is authenticated as `Corleanus` (per `gh auth status`).
- Whether Corleanus has WRITE access to `grigorijejakisic/Claudex` is the unknown.
- `gh release create --repo grigorijejakisic/Claudex` and `gh repo edit grigorijejakisic/Claudex` use gh's HTTPS+token path — they may fail with `403 Forbidden` or `gh: not found` if Corleanus lacks write permission on that repo.

**This plan handles both cases.** The task list below tries the gh-as-Corleanus path first; if it fails with permission error, the plan halts non-destructively and the runbook documents the operator fallback (`gh auth login --hostname github.com --user grigorijejakisic` then re-run the same gh commands). The release and topics are not load-bearing for the v4.1 ship narrative — they enhance it. A delayed release-creation by a few hours is acceptable; CONTEXT.md `<acceptance>` items 4 and 5 can be satisfied operator-side after this plan halts.

<task id="02-extract-changelog-notes">
**Extract the v4.1.0 CHANGELOG section into a temp notes file** for `gh release create --notes-file`:

```bash
NOTES_FILE=$(mktemp --suffix=.md)
awk '
  /^## \[4.1.0\] — 2026-05-02/ { flag=1; next }

  flag { print }
' CHANGELOG.md > "$NOTES_FILE"

NOTES_FILE="$(mktemp -t release-notes.XXXXXX)"

NOTES_FILE="${NOTES_FILE}.md"
# ... then proceed with the awk extraction above
```

If the awk extract is empty (likely cause: CHANGELOG.md doesn't have the expected `## [4.1.0] — 2026-05-02` line), Plan 17-01 didn't land correctly — SendMessage team-lead, HALT, do NOT hand-author release notes.

Required content (target ≤80 lines):

```markdown
# Branch Protection Setup — Vesna CI Required

This runbook describes how to apply the branch protection rule that gates merges to `master` on the public repo `grigorijejakisic/Claudex` behind a passing Vesna CI run. It is HITL — the GitHub UI is the only practical path to apply this rule (gh CLI's API support is for "rulesets," a different mechanism with separate semantics).

## Why this exists

Phase 10 shipped Vesna CI as the behavioral gate for v4 ships (17 probes, 100% PASS aggregate, 100% per non-empty category). It runs on every push to `master` via `.github/workflows/vesna.yml`. Branch protection makes that gate enforced — strangers (or the maintainer in a tired moment) cannot merge a PR that breaks behavioral parity.

It is HITL because:

- The simplest path is the GitHub UI's "classic" branch protection settings — five clicks, two minutes.
- gh CLI's branch protection support targets "rulesets" (the newer mechanism); we want the classic rule (matches Phase 10's pre-set expectation and the Vesna workflow's existing trigger semantics).
- The rule MUST be applied by an account with admin rights on `grigorijejakisic/Claudex` — that is the operator (`grigorijejakisic`), not Corleanus (the working dev account that lacks admin on the public repo by design).

## Click path

1. **Navigate** to `https://github.com/grigorijejakisic/Claudex/settings/branches`. Sign in as `grigorijejakisic` if not already.
2. **Click** "Add rule" (under "Branch protection rules"). If a rule for `master` already exists, click "Edit" instead.
3. **Branch name pattern:** type `master` exactly.
4. **Check** "Require a pull request before merging" (optional but recommended; Phase 11 SC#4 cold-start trial pattern).
5. **Check** "Require status checks to pass before merging."
6. **Check** "Require branches to be up to date before merging" (this is the strict mode that prevents merge-skew bugs).
7. **In the search box** under "Status checks that are required," type `Vesna`. Select the matching check from the dropdown — typically `Vesna / probes` or just `Vesna` depending on how the workflow's `name:` field was set in `.github/workflows/vesna.yml`.

   **Note:** the Vesna check will only appear in the dropdown AFTER the Vesna workflow has run at least once on the public repo. The workflow runs on every push to `master`, so the first push from Plan 17-02 should trigger it — wait for that run to complete before opening this settings page, or the search will return no matches.

8. **Leave** "Do not allow bypassing the above settings" UNchecked. This lets the operator (admin) override in emergencies (cold-fix the live repo without spinning up a new branch). Strangers without admin still cannot bypass.
9. **Click** "Create" (or "Save changes" if editing).

The rule is now active. Subsequent pushes to `master` that are not via PR, or PRs whose Vesna check fails, will be rejected by GitHub.

## Verification

```bash
gh api repos/grigorijejakisic/Claudex/branches/master/protection \
  --jq '.required_status_checks.contexts'
# Expected: ["Vesna"] (or whatever the workflow's name resolves to)
```

If this returns `null` or empty, the rule didn't apply — re-walk the click path. If it returns `404 Not Found`, branch protection is not active on `master`.

## Maintenance

If the Vesna workflow's `name:` changes (in `.github/workflows/vesna.yml`), the branch protection rule must be updated to match — the rule references the check by name, not by path. Re-walk steps 1, 2 (Edit), 7 (search for the new name), 9 (Save changes).

If a future v4.2+ ships additional CI gates (e.g., LongMemEval baseline, doctor self-check), each new check must be added to the "required status checks" list via the same click path.
```

## Notes for the implementer

- **The release notes are extracted, not hand-authored.** Hand-rewriting the CHANGELOG content into "release notes prose" creates a divergence between the changelog and the release page that strangers will notice. The awk extract gives byte-identical content; that's correct.
- **`--verify-tag` is load-bearing.** Without it, `gh release create v4.1.0` will silently create a release that points at a tag-that-doesn't-exist-yet, then GitHub auto-creates the tag at HEAD of `master` — which is the wrong commit if Plan 17-04 has already landed an admin commit on top of v4.1.0's content. The flag refuses to create the release until the tag pre-exists.
- **gh CLI permission failure is not a blocker for this plan.** The plan ships the runbook (REL-07) regardless. Tasks 03 and 04 (release + topics) are best-effort; failures get documented and routed to operator fallback. The plan completes successfully even if the operator must finish 17-03's gh steps.
- **Plan 17-04 is the only plan that pushes to both remotes.** Keeping the gh-applied release + topics out of the local commit means the public push from Plan 17-02 already established the publish-pointer; release + topics are GitHub-side metadata (not git tree state). The runbook is the only file artifact, and it commits in this plan but pushes in 17-04.
- **The runbook's docs/onboarding/ location is intentional.** Phase 16 shipped `docs/onboarding/{macos,linux,windows}.md`; this runbook joins them as the fourth file in that folder. The README link `[docs/onboarding/](./docs/onboarding/)` (in the Status banner) lands strangers in a folder of operator-runnable runbooks — the public-ship runbook fits the existing pattern.
