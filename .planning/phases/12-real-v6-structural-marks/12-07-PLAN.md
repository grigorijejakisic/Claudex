Fix the retrieval ranking fidelity failure (Phase 12 mark 7). The Big Mozzy V2 diagnostic (2026-05-14) documented one experience pattern ("big-balkan has no limitations") appearing at position 0 across at least 16 domain-unrelated queries — TT cycles, Maxbet SSE endpoints, polymorphic Account architecture, etc. This is not a retrieval algorithm failure; it's a scoring formula failure: the pattern has a high `importance_score` that dominates the RRF + three-factor computation across topically-unrelated queries.

The fix: a post-rerank topical-distance multiplier that caps importance contribution when the candidate is topically far from the query. Importance can still dominate *within* a topical band; it cannot override topical irrelevance.

Anti-scope: RRF stays. Reranker stays. Bi-encoder stays. The fix is at the rescoring step only.
</objective>

Based on Task 1's understanding of the scoring architecture, implement the post-rerank topical-distance multiplier.

The formula (from 12-CONTEXT.md operator-locked answer Q [12-07/Q1]):
```
effective_score = topical_score + importance_score * max(0, 1 - (topical_distance - threshold) / falloff)
```

Where:
- `topical_score` = the RRF + three-factor score contribution from topical relevance channels (FTS5 + vector)
- `importance_score` = the artifact's `importance_score` field * beta weight
- `topical_distance` = 1 - cosine_similarity(query_embedding, artifact_embedding) — computed from the bi-encoder embeddings already present in the pipeline
- `threshold` = config `v6.routing.importance_topical_threshold` (derived empirically in this task)
- `falloff` = config `v6.routing.importance_falloff` (derived empirically in this task)

**Empirical threshold + falloff derivation:**

Run the regression harness against variations of threshold and falloff to find values where:
- big-balkan does NOT appear at position 0 for the 8 domain-unrelated queries
- big-balkan still appears in top-5 for "big-balkan betting limitations"

Starting point: threshold=0.5, falloff=0.3. If big-balkan still crowds at threshold=0.5, try 0.4 or 0.3. Document the final values and the derivation in the SUMMARY.

**Implementation approach (adapt to Task 1 findings):**

If `topical_distance` is not yet computed in the scoring path:
- During the vector/embedding channel, the cosine similarity between query and artifact embedding is already computed as part of KNN ranking. Capture this as `topical_similarity` = cosine(query_emb, artifact_emb), then `topical_distance = 1 - topical_similarity`.
- If embeddings aren't available at the scoring step (sync path), apply the multiplier only in the async path and leave the sync path unchanged (sync path uses FTS5 + recency only per the existing architecture).

If `topical_distance` computation would require a new embedding call:
- Use a simpler proxy: the candidate's RRF score from the vector channel as a topicality proxy. If the vector channel gave this artifact a low rank (high RRF rank number = low score), it's topically distant. `topical_distance = 1 - (rrf_vector_score / max_rrf_score)` where max_rrf_score is `1/(60+1)`.

The exact formula implementation depends on what Task 1 discovered. The key invariant: **importance contribution is capped when the artifact is topically far from the query**. Honor the formula; adapt the inputs to what's available.

Add the new config values:
```typescript
const importanceTopicalThreshold = getPolicy('v6.routing.importance_topical_threshold') ?? 0.5;
const importanceFalloff = getPolicy('v6.routing.importance_falloff') ?? 0.3;
```

Apply in both full pipeline and bi-encoder fallback paths — same formula, same config values.
