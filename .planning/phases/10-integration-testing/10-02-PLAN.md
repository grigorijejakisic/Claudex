**src/tests/integration/cross-cutting.test.ts** — Integration tests covering Architecture Section 14 scenarios 4-11.

**Setup pattern**: Same as 10-01: `beforeEach` creates fresh in-memory DB, `initializeSchema`, common test values, `afterEach` closes DB. Config has `enrichment.provider: 'none'`.

---

**describe('Cross-Session Learnings Persistence')** — Scenario 4.

**Test: `learnings from session 1 appear in session 2 assembly`**

Session 1:
1. `createSession(db, { session_id: 'sess-1', project: 'proj', cwd: '/test', source: 'cc-hooks' })`
2. Insert learnings directly: `insertLearning(db, { project: 'proj', content: 'Always use strict TypeScript', fingerprint: 'learning-1' })` and `insertLearning(db, { project: 'proj', content: 'Run tests before committing', fingerprint: 'learning-2' })`
3. `promoteLearnings({ db, project: 'proj', sessionLearnings: ['Always use strict TypeScript'] })` — promotes the learning
4. `endSession(db, 'sess-1', 'completed')`

Session 2:
5. `createSession(db, { session_id: 'sess-2', project: 'proj', cwd: '/test', source: 'cc-hooks' })`
6. `const payload = assembleFullContext({ db, project: 'proj', projectDir: '/test', config })`
7. Verify: `getTopLearnings(db, 'proj', 10)` returns at least 1 learning. If payload.content is non-empty, check that sources includes 'learnings' (may not if budget order excludes it — the key assertion is that learnings survive across sessions in the DB).

---

**describe('Checkpoint Recovery')** — Scenario 5.

**Test: `checkpoint write -> recoverFromDb restores committed state`**

1. `createSession(db, { session_id: 'cp-sess', project: 'proj', cwd: '/test', source: 'cc-hooks' })`
2. Insert some observations and thread state to populate the checkpoint
3. `await writeCheckpoint({ db, sessionId: 'cp-sess', project: 'proj', projectDir: '/test', trigger: 'compaction', scope: null })`
4. Verify: checkpoint_meta table has a row with status 'committed' or 'mirrored' for session 'cp-sess'
5. `recoverFromDb(db)` — should not error, should re-mirror any committed rows
6. Verify: after recovery, checkpoint_meta row status is 'mirrored' (or still committed if mirroring failed due to no real filesystem — that's OK for in-memory DB test)
7. `const loaded = loadCheckpoint(db, '/test')` — verify returns a checkpoint object (may be null if no file mirror, but DB query should succeed)

---

**describe('Topic-Shift Micro-Injection')** — Scenario 6.

**Test: `Jaccard fallback topic-shift produces pivot block <= 800 tokens`**

1. `createSession(db, ...)` and seed thread_state with a topic:
   `upsertThreadState(db, { session_id: 'ts-sess', topic: 'authentication bug', summary: 'Fixing OAuth token refresh', key_exchanges: '[]' })`
2. Insert a few learnings about the new topic for pivot content
3. Create detector: `const detector = new TopicShiftDetector(null)` (null = Jaccard fallback)
4. Detect shift: `const result = await detector.detectTopicShift({ prompt: 'Now let us switch to the deployment pipeline configuration', db, sessionId: 'ts-sess', config: { topicShiftThreshold: 0.35, topicShiftWindow: 3 } })`
5. If shifted (explicit keyword "switch to" should trigger):
   - Call `assembleRegularPrompt({ isPostCompaction: false, prompt: 'Now let us switch to the deployment pipeline', gauge: null, topicShift: result, db, project: 'proj', projectDir: '/test', config })`
   - Verify: if payload has content, tokenEstimate <= 800
6. If not shifted (Jaccard may not fire without sufficient history): test is still valid, just verifies the detector returns a `TopicShiftResult` object without error

---

**describe('Enrichment Fallback')** — Scenario 7.

**Test: `checkpoint writes successfully without enrichment provider`**

1. `createSession(db, ...)`, insert observations and thread state
2. `await writeCheckpoint({ db, sessionId: 'enr-sess', project: 'proj', projectDir: '/test', trigger: 'compaction', scope: null })` — no enrichmentProvider passed
3. Verify: checkpoint_meta row exists with non-null `data` field (heuristic data preserved)
4. Parse the YAML data field: verify it contains at minimum meta section and working section
5. The key assertion: checkpoint was written successfully without LLM enrichment, heuristic data was not lost

---

**Test: `FTS5 search returns relevant observations ranked by BM25`**

1. `createSession(db, ...)`

   - "Implemented OAuth token refresh flow" (importance 4)
   - "Fixed CSS styling on login page" (importance 3)
   - "Added rate limiting to API endpoints" (importance 4)

   - "Refactored database connection pooling" (importance 3)

4. Verify: results contain the 2 OAuth-related observations
5. Verify: "OAuth token refresh" observation appears (ranked high — most relevant)
6. Verify: "CSS styling" and "database connection" observations do NOT appear in results for 'OAuth' query

**describe('Telemetry Queryable (OBSV-03)')** — Scenario 9.

**Test: `Architecture Section 10c SQL queries return valid results against populated telemetry`**

1. `createSession(db, { session_id: 'tel-sess', ... })`
2. Populate telemetry table with realistic events:
   ```
   emitTelemetry(db, 'tel-sess', 'hook_invocation', { hook: 'SessionStart', duration_ms: 85, result: 'inject' }, 85)
   emitTelemetry(db, 'tel-sess', 'hook_invocation', { hook: 'PostToolUse', duration_ms: 12, result: 'skip' }, 12)
   emitTelemetry(db, 'tel-sess', 'hook_invocation', { hook: 'PostToolUse', duration_ms: 15, result: 'skip' }, 15)
   emitTelemetry(db, 'tel-sess', 'hook_invocation', { hook: 'Stop', duration_ms: 42, result: 'skip' }, 42)
   emitTelemetry(db, 'tel-sess', 'injection', { trigger: 'session_start', sections_included: ['identity', 'checkpoint'], total_tokens: 1200, budget_remaining: 2800 }, 85)
   emitTelemetry(db, 'tel-sess', 'decision_capture', { content: 'Use ULID', source: 'direction', stage1_match: true, stored: true }, 5)
   emitTelemetry(db, 'tel-sess', 'decision_capture', { content: 'Let me read', stage1_match: true, stored: false, reason: 'filler_rejected' }, 2)
   emitTelemetry(db, 'tel-sess', 'checkpoint_write', { checkpoint_id: '01TEST', trigger: 'compaction', state: 'committed', write_duration_ms: 40 }, 40)
   ```

3. Execute Query 1 — Last injection detail:
   ```sql
   SELECT detail FROM telemetry
   WHERE session_id = ? AND event_kind = 'injection'
   ORDER BY timestamp_epoch DESC LIMIT 1
   ```
   Verify: returns JSON with trigger='session_start', sections_included array, total_tokens.

4. Execute Query 2 — Hook latency stats:
   ```sql
   SELECT
     json_extract(detail, '$.hook') as hook,
     COUNT(*) as count,
     ROUND(AVG(latency_ms), 1) as avg_ms,
     ROUND(MAX(latency_ms), 1) as max_ms
   FROM telemetry
   WHERE session_id = ? AND event_kind = 'hook_invocation'
   GROUP BY json_extract(detail, '$.hook')
   ```
   Verify: 3 rows (SessionStart, PostToolUse, Stop). PostToolUse count=2, avg_ms between 12 and 15.

5. Execute Query 3 — Decision capture precision:
   ```sql
   SELECT
     json_extract(detail, '$.stored') as stored,
     COUNT(*) as count
   FROM telemetry
   WHERE event_kind = 'decision_capture' AND session_id = ?
   GROUP BY stored
   ```
   Verify: 2 rows — stored=true count=1, stored=false count=1.

6. Execute Query 4 — Checkpoint lifecycle:
   ```sql
   SELECT
     json_extract(detail, '$.checkpoint_id') as checkpoint_id,
     json_extract(detail, '$.state') as state,
     timestamp_epoch
   FROM telemetry
   WHERE event_kind = 'checkpoint_write'
     AND json_extract(detail, '$.state') != 'mirrored'
   ORDER BY timestamp_epoch DESC
   ```
   Verify: returns 1 row with checkpoint_id='01TEST', state='committed'.

**Test: `decay prunes old low-importance observations while retaining important ones`**

   - Old low-importance: `insertObservation(db, { session_id: 'decay-sess', project: 'proj', tool_name: 'Read', category: 'other', title: 'Read config', content: 'Read some config file', importance: 1, files_modified: '[]', timestamp_epoch: Math.floor(Date.now()/1000) - 90*86400 })` (90 days old)
   - Old high-importance: `insertObservation(db, { ..., title: 'Critical security fix', content: 'Fixed SQL injection vulnerability', importance: 5, timestamp_epoch: Math.floor(Date.now()/1000) - 90*86400 })` (90 days old)

7. Verify: recent low-importance observation does NOT have deleted_at_epoch set (retained — within retention window)
