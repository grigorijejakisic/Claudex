## User Constraints (from CONTEXT.md)

### Locked Decisions

- **Hybrid schema** — YAML status header (`status`, `phase`) + Markdown ADR body. Header is machine-queryable; body is human-readable. Both are first-class.
- **YAML required fields:** `status: active | archived | paused`, `phase: <N>`. `created_at_epoch_ms: <ms>` and `topic: <slug>` optional.
- **Body structure (locked order):** `# <date> — <topic>` title, then four bold-label sections in order — `**What we found:**`, `**What we decided:**`, `**What's next:**`, `**Where to look:**`.
- **Length target:** ~15 lines body (not a hard cap; "no longer than necessary").
- **Writer location:** `src/angel/handoff-writer.ts` (or planner-chosen equivalent). Triggered by `/handoff` skill or programmatic pause-work. Validates required fields before write. Atomic write (rename pattern).
- **Migration:** read existing `context/handoffs/ACTIVE.md`. If new YAML shape: leave alone. If old 372-line schema: extract status + phase, distill body into the four `**What ...**` sections, archive original verbatim to `context/handoffs/archive/<date>-<topic>.md`. No destructive transformation.
- **MEMORY.md `## Handoff` consumption:** Phase 4.1's writer reads `ACTIVE.md` YAML header → renders one-line summary in `## Handoff`. `archived` → `No active handoff.`; `active` → `Active handoff at phase {phase}: {topic}. See: context/handoffs/ACTIVE.md`; `paused` → `Handoff paused at phase {phase}. See: context/handoffs/ACTIVE.md`. **One line, never the full body.**
- **Vesna handoff-pickup probes** — verify a fresh session reads new-format ACTIVE.md and picks up the next-action without exploratory tool use. Per CONTEXT.md SC#4: ≥3 probes across ≥3 different projects covering active / paused / archived states.
- **Single-active design** — one ACTIVE.md per project. Multi-handoff deferred.

### Claude's Discretion

- Exact YAML field name conventions (recommendation: `created_at_epoch_ms` for v4 symmetry).
- Optional fields beyond `topic` (recommendation: skip in 7.5; add only if Phase 8.5 needs them).
- Migration script vs manual migration (recommendation: scripted, planner reviews each migration before commit).

### Deferred Ideas (OUT OF SCOPE)

- Multi-handoff (per-task / per-feature). Single ACTIVE.md only.
- Handoff search/query infrastructure beyond YAML frontmatter parsing.
- Cross-project handoff correlation.

## Summary

Phase 7.5 is a small, surgical schema-and-writer change with two existing consumer surfaces that must remain green:

1. `src/angel/memory-md-writer.ts:renderHandoff` — currently parses old `## Commander's Intent` + `## What's Left To Do` body. Must be rewritten to read the YAML header and render a one-line summary per CONTEXT.md.
2. `src/adapters/cc-hooks/session-start.ts:computeInitialUserMessage` (Phase 5 SC#4) — currently consumes `summary:` field from YAML frontmatter. The new format must keep `summary:` as an optional field (recommended REQUIRED in practice) so Phase 5's prime-message contract continues to fire.

The current `context/handoffs/ACTIVE.md` (the 2026-04-27 audit-rebind handoff) **already uses the new YAML+ADR format** — its header is `status: active`, `phase: 4.1` and the body uses `## Where we are right now`, `## What we found`, `## What we decided`, `## What's next — literal`, `## How to pick up tomorrow` (sections, not bold labels). This means migration is mostly cosmetic re-labeling rather than a full distillation pass. The 372-line "old schema" exists in archive form only (no longer in current ACTIVE.md).

**Primary recommendation:** Single-pass implementation. (1) Define schema in `src/angel/handoff-writer.ts` as a small typed module with `writeHandoff()`, `parseHandoffHeader()`, `validateHeader()`. (2) Rewrite `renderHandoff()` in `memory-md-writer.ts` to consume parsed header. (3) Migrate the existing ACTIVE.md (cosmetic — relabel `## Where we are right now` → drop, lift body content into `**What we found:**` / `**What we decided:**` / `**What's next:**` / `**Where to look:**`). (4) Add 3 Vesna probes covering active/paused/archived. (5) Run full SC#1-#4 gate.

### Pattern 1: Hand-rolled YAML header parser (existing precedent)

`src/adapters/cc-hooks/session-start.ts:computeInitialUserMessage` already parses the handoff frontmatter for the SC#4 prime. Mirror its shape:

```typescript
function parseHandoffHeader(raw: string): HandoffHeader | null {
  const m = raw.match(/^---\n([\s\S]*?)\n---\n/);
  if (!m) return null;
  const fields: Record<string, string> = {};
  for (const line of m[1].split('\n')) {
    const kv = line.match(/^([a-z_]+):\s*"?([^"]*)"?\s*$/);
    if (kv) fields[kv[1]] = kv[2].trim();
  }
  if (!fields.status || !fields.phase) return null;
  return {
    status: fields.status as 'active' | 'archived' | 'paused',
    phase: fields.phase,
    summary: fields.summary,
    topic: fields.topic,
    created_at_epoch_ms: fields.created_at_epoch_ms ? Number(fields.created_at_epoch_ms) : undefined,
  };
}
```

### Pattern 2: Atomic write (memory-md-writer precedent)

```typescript
function atomicWriteHandoff(targetPath: string, content: string): void {
  const tmpPath = targetPath + '.tmp';
  fs.writeFileSync(tmpPath, content, 'utf8');
  fs.renameSync(tmpPath, targetPath);
}
```

### Pattern 3: Render one-line summary in MEMORY.md (CONTEXT.md spec)

```typescript
export function renderHandoff(project: string): string {
  const header = '## Handoff\n\n';
  const projectPath = resolveProjectPath(project);
  if (!projectPath) return header + 'No active handoff.\n';
  const handoffPath = path.join(projectPath, 'context', 'handoffs', 'ACTIVE.md');
  if (!fs.existsSync(handoffPath)) return header + 'No active handoff.\n';
  let raw: string;
  try { raw = fs.readFileSync(handoffPath, 'utf8'); }
  catch { return header + 'No active handoff.\n'; }
  const parsed = parseHandoffHeader(raw);
  if (!parsed) return header + 'No active handoff.\n';
  const phase = parsed.phase;
  const topic = parsed.topic ?? parsed.summary ?? 'unspecified';
  switch (parsed.status) {
    case 'active':
      return header + `Active handoff at phase ${phase}: ${topic}.\nSee: context/handoffs/ACTIVE.md\n`;
    case 'paused':
      return header + `Handoff paused at phase ${phase}.\nSee: context/handoffs/ACTIVE.md\n`;
    case 'archived':
    default:
      return header + 'No active handoff.\n';
  }
}
```

### Anti-Patterns to Avoid

- **Distilling body into MEMORY.md** — old `distillHandoffBody()` walks the body. Per CONTEXT.md, body lives in ACTIVE.md only; MEMORY.md is one-line index entry. Delete `distillHandoffBody` and `MAX_HANDOFF_LINES`.
- **Hard-rejecting old-schema ACTIVE.md** — the writer should detect old schema (presence of `## Commander's Intent` etc.) and emit a clear error pointing to the migration script, NOT silently overwrite.
- **Coupling writer to a specific trigger** — writer takes a `HandoffInput` object (status, phase, topic, the four section texts) and writes the file. The `/handoff` skill is the trigger; the writer is shape-agnostic.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic file write | new lock file system | `fs.writeFileSync(tmp); fs.renameSync(tmp, target)` | POSIX-atomic on rename; already pattern in codebase |
| Date format in title | custom date formatter | `new Date().toISOString().slice(0, 10)` | YYYY-MM-DD is locked per CONTEXT.md |
| YAML serialize | custom indented YAML emitter | string template literal — header is 2-4 simple `key: value` lines, no nesting | Avoids dep weight for trivially simple shape |

**Key insight:** The whole change is plumbing. No clever logic; just a typed schema, a Markdown emitter, and a one-line rewrite of `renderHandoff()`. Don't over-engineer.

## Common Pitfalls

### Pitfall 1: SC#4 prime-message contract regression

**What goes wrong:** Phase 5 shipped `computeInitialUserMessage()` reading `summary:` from frontmatter. If Phase 7.5's writer makes `summary:` optional and the migration drops it from the existing ACTIVE.md, SC#4 stops priming.

**Why it happens:** CONTEXT.md says `summary:` is not required (only `status` + `phase`). The contract drift is: CONTEXT.md spec vs. Phase 5 prime-message dependency.

**How to avoid:**
- Keep `summary:` as a recommended-strongly field in writer signature (caller must explicitly opt out).
- Migration of existing ACTIVE.md MUST preserve `summary` if present (and the current 2026-04-27 ACTIVE.md does NOT have a `summary:` field — it only has `status: active` + `phase: 4.1`. Migration must add one derived from the title line). **Confirmed by reading current ACTIVE.md — gap exists today.**
- Add a regression test: run `computeInitialUserMessage` against migrated ACTIVE.md, assert non-null prime.

**Warning signs:** SC#4 test at `src/tests/integration/handoff-pickup-one-turn.test.ts` starts returning null in CI.

### Pitfall 2: MEMORY.md cache-stability drift (CACH-01)

**What goes wrong:** Rewriting `renderHandoff()` changes the byte output. CACH-01 (golden snapshot byte-identical) breaks until the snapshot is regenerated.

**How to avoid:** Regenerate `assembler-cache-fixtures` golden snapshot in the same atomic commit. Run `src/tests/assembly/assembler.cache-stability.test.ts` to confirm.

### Pitfall 3: Migration data loss

**What goes wrong:** Migrating the existing `ACTIVE.md` overwrites it before the archive copy lands.

**How to avoid:** Order strictly: (1) copy current ACTIVE.md verbatim to `context/handoffs/archive/<date>-<topic>.md`; (2) git-add the archive; (3) write migrated ACTIVE.md. If any step fails, abort. Atomic commit with both files.

### Pitfall 4: `## Handoff` section becomes empty in MEMORY.md across all projects

**What goes wrong:** Today, every project's `## Handoff` says "No active handoff." because the existing ACTIVE.md is the new format but `distillHandoffBody` looks for the old `## Commander's Intent` header (which doesn't exist in the new file). After Phase 7.5 ships, every project that has any ACTIVE.md will suddenly start rendering content.

**How to avoid:** Sweep all known projects (claudex-v3, lacuna-betting, oracle, big-mozzy-v2, desktop-01dcc792, nexus-e53c6c93) for ACTIVE.md files. If old schema, schedule migration. If new schema, MEMORY.md will start rendering correctly automatically (no per-project action needed).

**Warning signs:** Cross-project regression: a project has `## Handoff` rendering an unexpected string post-7.5. Mitigation: per-project `_old.md` archive copy of pre-7.5 ACTIVE.md before any migration runs.

### Pitfall 5: Vesna probe stub mismatch

**What goes wrong:** Vesna probes test the *behavioral* contract — does a fresh session pick up the next-action? But "next-action" lives in the body (`**What's next:**`), and the SC#4 prime fires from the YAML header's `summary:`. If the probe asserts the header value but the body has the actual next action, mismatch can mask drift.

**How to avoid:** Probe asserts both: (a) prime fires non-null, (b) the prime contains the body's first `**What's next:**` line as substring. Tight coupling but it catches schema/body desync.

## Open Questions

1. **Should `summary:` field be required in the YAML header schema?**
   - What we know: CONTEXT.md says only `status` + `phase` required. Phase 5 SC#4 prime depends on `summary:`.
   - What's unclear: If `summary:` absent, does SC#4 prime fall back to `topic:`? To body's first `**What's next:**` line? To no-prime?
   - **Recommendation:** Writer signature treats `summary` as required (TS type forces it); schema spec leaves it "optional" for backward-read compatibility but writer always emits it. This matches Pitfall 1 mitigation.

2. **Where does the `/handoff` skill live, and does it call the new writer?**
   - What we know: Skill mentioned in CONTEXT.md as one of the two trigger surfaces. Glob at `.claude/skills/handoff*` returned nothing locally — skill may be global or in user's `~/.claude/skills/`.
   - What's unclear: Whether Phase 7.5 modifies the skill or just provides the writer the skill calls.
   - **Recommendation:** Phase 7.5 ships only the TS writer. Skill update (if any) is out of scope; user/separate skill author updates `~/.claude/skills/handoff/` to call the new shape.

3. **Migration script vs in-PR commit?**
   - What we know: CONTEXT.md leaves to discretion; recommendation in CONTEXT.md is "scripted, planner reviews each migration before commit."
   - **Recommendation:** Keep it as a one-shot Node script (`scripts/migrate-handoff.ts`) that can be re-run idempotently; include both archive copy and migrated content in the same atomic commit for the claudex-v3 project ACTIVE.md.
