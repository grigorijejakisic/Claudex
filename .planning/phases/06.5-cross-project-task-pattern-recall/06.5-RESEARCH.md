**HYBRID equivalence (LOCKED — design decision from 2026-04-29 session):**

Stage 1 — Fast filter: telemetry-handle overlap. For each candidate artifact pair across projects, count shared telemetry handles (tools_used, files_touched topology, user_framing_tokens, error_types). Threshold: ≥3 shared handles → candidate match (proceeds to Stage 2). <3 shared handles → not a match.

Stage 2 — Precision check: cosine embedding similarity on salience text using snowflake-arctic-embed2 (1024d). Threshold: ≥0.85 → confirmed equivalent. 0.70 ≤ cosine < 0.85 → ambiguous; not surfaced, but logged for tuning. < 0.70 → false positive from Stage 1; reject.

### Pattern 3: Task-shape detector (regex first, LLM-deferred)

**What:** Pure regex over normalized query string. Patterns drawn from 4.1's shape vocabulary canonical values (e.g., `task_shape='scraping-rate-limit-investigation'` matches `/scrap|crawl|fetch.*rate|throttl/i` + `/(api|backend|endpoint|server)/i`). **When to use:** At top of `claudex_search` handler; if `isTaskShaped`, run cross-project expansion. Otherwise short-circuit to existing project-local search.

### Anti-Patterns to Avoid

- **Re-encoding handles in 6.5.** Phase 4.1's lesson-writer already harvests TelemetryHandles + ShapeHandles. Do NOT add a parallel harvest path. Read what 4.1 writes.
- **Coupling Experience Tier to Critical Reminders Tier.** Architecture B = parallel, sharing infrastructure but NOT scoring inputs. Don't bolt the new scorer onto `critical-reminders.ts` — separate file, separate budget, separate top-K.
- **Calling the reranker for HYBRID Stage 2.** Stage 2 is a cosine check on existing 1024d embeddings, not a cross-encoder rerank. The reranker is downstream of `claudex_search` results merge, not part of HYBRID equivalence proper.
- **Adding to `claudex_search` response shape.** RETR-04 (Phase 6) locked the MCP surface canonical fixture. Cross-project results merge into the existing result list, with provenance in result body, not as a new top-level field. Verify against `mcp-surface-canonical.json`.
- **Imperative framing.** The surface template is locked. No "WARNING:", no "Always do X", no "supersedes". Observational only.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: Confusing the legacy `artifacts` table with V17's `artifact` view

**What goes wrong:** CONTEXT.md says "ALTER TABLE artifact ADD COLUMN task_pattern TEXT" but the actual writable table in current schema is the legacy `artifacts` (plural, with `artifact_type`) — see `schema.ts:293`. The V17 migration introduced an `artifact` view (singular, with `kind`) over the unified kernel.

**Why it happens:** Two-table-name regime is a known gotcha (Phase 4.1 Plan 07 hit it with `critical_rules_multi_project` sidecar — same root cause).

**How to avoid:**
- ALTER goes on `artifacts` (legacy plural) which is the underlying writable table
- The V17 view `artifact` (singular) propagates the column read-only via the JSON sidecar pattern
- For Phase 6.5: prefer adding `task_pattern` as a sidecar table `artifact_task_pattern (artifact_id, task_pattern, classified_at_epoch_ms, classifier_confidence)` — same shape as `critical_rules_multi_project`. Avoids V17 view UPDATE composition issues.
- **Recommended:** Sidecar table over column ALTER — matches Phase 4.1's pre-authorized fallback pattern.

**Warning signs:** Migration runs but reads return null; INSERT triggers complain about missing column; FTS rebuilds fail.

### Pitfall 2: Cache-stability regression at session-start

**What goes wrong:** Adding a new section at P4.06 risks breaking CACH-01/CACH-02 (Phase 5 invariance under volatile-state mutation: clock change, session-ID, host-env must NOT change output bytes).

**Why it happens:** Experience Tier might surface different cross-project lessons on different runs if telemetry recency or query expansion sees different DB state.

**How to avoid:**
- Order results by `(score DESC, artifact_id ASC)` deterministic tiebreaker
- Strip any timestamps from rendered surface (only `last_used_within_14d` boolean — no actual epoch)
- Test with `phase-5-full-gate.test.ts` extended with one new test that runs the assembler twice and asserts byte-identical output
- Probe set in Vesna gate must be hermetic — fresh DB per test, deterministic seed for any randomness

**Warning signs:** `phase-5-full-gate.test.ts` 7/7 → fewer; CACH-02 layer 2 invariance test fails; flaky CI.

### Pitfall 3: Stage-2 cosine threshold drift

**What goes wrong:** 0.85 is a starting point per CONTEXT.md. If real-world handle distributions are different from the canonical shadowban probe, the threshold either over-matches (false positives surface noisy lessons) or under-matches (canonical probe fails).

**Why it happens:** The probe set is tiny (3 cross-project probes) and crafted; production noise is broader.

**How to avoid:**
- Log Stage-2 ambiguous (0.70 ≤ cosine < 0.85) to telemetry with `event_kind='cross_project_ambiguous'` and `detail.{a_id, b_id, cosine, project_a, project_b}` — recommendation per CONTEXT.md
- Add a planner-level discretion check: A/B 0.85 vs 0.80 vs 0.90 against the 3 Vesna probes; document choice in 06-5-SUMMARY.md
- Threshold tuning is **not** a hard gate; the SC#1 gate is "≥3 cross-project probes pass," not "0.85 is empirically best"

**Warning signs:** Probe 1 (shadowban) passes but probes 2 + 3 don't; ambiguous-band log shows 80%+ of real cross-project pairs land in 0.70-0.85.

### Pitfall 4: Lexical leakage in Vesna probe prompts

**What goes wrong:** The prompts test perceptual handles, not lexical overlap. If the prompt contains tokens that already appear in the lesson body, the test passes for the wrong reason.

**Why it happens:** Easy to write "investigate rate-limit pattern" as the prompt and have the lesson body contain "rate-limit" — FTS5 alone surfaces it.

**How to avoid:**
- Pre-flight assertion: prompt must contain ZERO of `["rate", "limit", "Mozzart", "429", "shadowban", "Cloudflare"]` for shadowban probe
- Probe 2 (auth-token-expiry): prompt must contain ZERO of `["token", "expiry", "session", "auth", "logout"]`
- Probe 3 (schema migration): prompt must contain ZERO of `["migration", "schema", "ALTER", "transaction", "downtime"]`
- Pre-flight is a Vitest `expect(prompt).not.toMatch(forbiddenWords)` assertion at the top of each `it` block

**Warning signs:** Probe passes but you cannot articulate WHY — the matcher succeeded on lexical not perceptual handles.

### Pitfall 5: Reranker fallback masking a real outage

**What goes wrong:** Phase 6.5 cross-project candidates feed the existing reranker pipeline; if the reranker is down, bi-encoder fallback might silently surface noisy cross-project results, conflating Phase 6.5 quality issues with reranker outage.

**Why it happens:** RETR-08 marked the reranker load-bearing but the bi-encoder fallback still runs; cross-project ambiguity makes the fallback mode worse for cross-project than within-project.

**How to avoid:**
- Phase 6.5 query expansion respects the `## Reranker Health` surface — when the 24h fallback count > 0, log a `cross_project_query_expansion` telemetry event with `detail.reranker_degraded=true`
- Vesna probes assert reranker is **healthy** before running the cross-project gate (skip-not-fail if degraded; documented as a `xfail` skip with clear reason)
- 06.5-SUMMARY.md notes any probe runs that hit fallback mode and excludes them from the SC#1 evidence

**Warning signs:** Vesna gate flakes on CI; manual reproduction works; production telemetry shows reranker_fallback rows.
