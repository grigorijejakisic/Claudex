<objective>
Establish a single owner for the "session ended" transition and run the downstream consequences in a known order. Today: stop hook may write `status='completed'`; UPS heartbeats `last_heartbeat_ts`; boundary detector decides ALIVE/DORMANT/TERMINATED but doesn't always promote; highlights extraction fires opportunistically when status flips. Different owners, different cadences, different reliability — Plan 14-00's RCA-2 work surfaced that Recent Session Frames is silently degraded for some sessions and the operator can't tell which step in the chain failed.

This plan makes the boundary-detector the sole authority. When it decides "this session is over," it promotes status AND triggers the ordered downstream chain (summary → pattern extraction → highlights → MEMORY.md → lesson pointers), with per-action telemetry so any failure is visible and localized.

| What this plan provides | Why |
|---|---|
| Single writer of `status='completed'` | One owner; idempotent; auditable |
| Ordered action chain with telemetry | Failures are localized, not silent |
| Stop hook stops writing status | Lifecycle ownership clean |
| Idempotency guard | Repeated TERMINATED detection doesn't re-fire actions |
| `session_end_action` telemetry | Operator can audit per-action outcomes from the DB |
</objective>

Add `promoteSessionToCompleted(db, sessionId)` function:

```typescript
/**
 * Single-owner session-end promotion.
 *
 * Idempotent: returns early if the session is already completed.
 * On promotion: writes status + ended_at_epoch_ms, then fires the
 * ordered action chain via fireEndOfSessionActions.
 *
 * Caller (heartbeat) invokes this when boundary-detector decides
 * the session is TERMINATED. No other writer should touch
 * sessions.status to 'completed'.
 */
export async function promoteSessionToCompleted(
  db: Database,
  sessionId: string,
  reason: 'idle_terminated' | 'crash_recovered' | 'explicit_close',
): Promise<void> {
  // Idempotency check
  const existing = db.prepare(
    `SELECT status, ended_at_epoch_ms FROM sessions WHERE session_id = ?`
  ).get(sessionId) as { status: string; ended_at_epoch_ms: number | null } | undefined;
  if (existing?.status === 'completed' && existing.ended_at_epoch_ms != null) return;

  const endedAt = Date.now();
  db.prepare(
    `UPDATE sessions SET status = 'completed', ended_at_epoch_ms = ? WHERE session_id = ?`
  ).run(endedAt, sessionId);

  await fireEndOfSessionActions(db, sessionId, endedAt, reason);
}
```

Add `fireEndOfSessionActions(db, sessionId, endedAt, reason)` that runs the 5 actions in order with try/catch isolation per action and telemetry per action.

<risks>
- **Risk 1: Hidden status-completed writers.** A test fixture, a CLI command, an Angel sub-task, or a third-party-style script may set the status. Mitigation: AC-9 final Grep audit catches survivors at static-check time.
- **Risk 2: Action ordering bug.** A naive Promise.all would parallelize them; the contract requires sequential ordering. Mitigation: explicit sequential `await` chain in fireEndOfSessionActions; test case 3 verifies order via telemetry timestamps.
- **Risk 3: Idempotency race.** Two concurrent heartbeat ticks both detect TERMINATED simultaneously. Mitigation: idempotency guard checks `sessions.status='completed' AND ended_at_epoch_ms IS NOT NULL` BEFORE the UPDATE; second concurrent caller sees the post-UPDATE state and skips. SQLite serializes writes so the race window is bounded by the SELECT-UPDATE gap; for absolute safety, wrap in a transaction with `SELECT ... FOR UPDATE`-equivalent (SQLite uses BEGIN IMMEDIATE).
- **Risk 4: Stop hook regression.** Removing the stop-hook status write could leave sessions in 'active' if the boundary-detector doesn't fire promptly (e.g., heartbeat is paused). Mitigation: existing TERMINATED detection thresholds are unchanged; sessions still complete on the same schedule. If operator wants explicit close-on-stop, propose Plan 14-05.1 with explicit-close path.
- **Risk 5: Telemetry table CHECK constraint migration is fragile.** SQLite cannot ALTER a CHECK; recreate-table-and-copy is the standard pattern. Mitigation: reference Plan 14-01's migration as a working precedent. Test the round-trip on a seeded DB.
- **Risk 6: 5-action chain takes too long, blocks heartbeat.** Each action could be slow (highlights extraction = LLM call up to ~2 min). Mitigation: per-action try/catch already prevents one failure from blocking next. Heartbeat tick should run promotion concurrently across sessions OR detach the chain from the tick loop entirely. For this plan: keep sequential within a session (correctness), but parallelize across sessions in the heartbeat loop. Document the latency expectation in SUMMARY.md.
</risks>
