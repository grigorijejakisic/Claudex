## Root cause analysis

The transcript_chunk reach gap (24 chunks across 122 unchunked candidate sessions) decomposes into two distinct failure modes:

### Failure mode 1: Enqueue gap (107 of 122 sessions)

**Where it breaks:** Sessions reach `status='completed'` without ever firing `memory_curation_pending`. The producers are correctly wired (session-end hook + Angel auto-close), but neither fires for sessions closed via:

- CC crash, kill, OS shutdown
- Session that pre-dated the 04-04 heartbeat-wiring (legacy DB rows from before enqueue logic existed)
- Sessions where SessionEnd fired but the hook itself errored before line 47 (pre-04-06 hook resilience era)

**Evidence:** 122 sessions have ≥10 turns with 0 chunks AND 0 enqueue events. Out of those, ~107 are sessions that never even entered the queue.

### Failure mode 2: Drain backlog (15 of 122 sessions)

23 enqueued events still `pending`, only 16 marked `done` — implying ~7 sessions are queue-stuck (failed enqueue→drain). Combined with the queue-isolation observation (sessions with `pending` events are a subset of unchunked sessions), this is a smaller secondary effect.

### Pre-existing bug (24 chunks, all wrong precision)

100% of existing transcript_chunk rows carry seconds-precision timestamps (10-digit). Without read-time normalization, recency-weighted retrieval would silently misorder these against ms-precision peers. Plan 02 Task 1 fixes the writer; Plan 01's `normalizeEpochMs` handles read-time normalization for legacy rows.

## What 4.1 fixes

- **Writer precision bug** — `transcript-chunker.ts:333` `* 1000` upscale at write time. New chunks land at ms-precision per CUR-14 lock. Regression test pinned at `(fixedSec + n) * 1000` in `tests/angel/transcript-chunker-timestamp.test.ts`.
- **Read-time normalization** — `normalizeEpochMs` (Plan 01) handles existing 24 legacy rows transparently at read time. No data migration needed.

## What 4.1 does NOT fix

- **Enqueue gap (~107 sessions)** — the producers are correctly wired but missed historical sessions and CC-shutdown-crash cases. This is a CUR-15 *reach* concern, NOT a precision concern. CUR-15 is **partially deferred** with rationale below.
- **Drain backlog (~7 sessions)** — 23 pending events stuck. Investigation of why heartbeat hasn't drained them is out of scope for this plan; likely needs a follow-up plan focused on Phase 5b drain reliability.

## Recommended follow-up

### CUR-15 status: PARTIALLY DEFERRED

**Closed in 4.1:**
- Writer fix (CUR-14 boundary): all NEW transcript_chunks land at ms-precision.
- Read-time normalization helper available (`normalizeEpochMs`).

**Deferred from 4.1 (planner-pre-authorized — see CONTEXT.md "Plan 02 authorizes partial CUR-15 defer if chunker reach can't be brought to ≥1 chunk/session in this phase scope"):**

- **Backfill enqueue for historical sessions** — should be a separate plan/follow-up. Recommended approach: heartbeat sweep that detects `status='completed' AND no transcript_chunk AND no memory_curation_pending event` and re-enqueues. Lightweight, idempotent (heartbeat already drains pending), and recovers the 107-session backlog without requiring code changes to the chunker itself.
- **Drain backlog investigation** — why are 7 enqueued events stuck pending? Likely root causes: failed Ollama call (no retry), session-deletion mid-drain, or missing project_id on `unknown_project`-shaped inserts. Phase 5b drain reliability is its own concern; deferred to a follow-up plan dedicated to that.

These deferrals do NOT block Phase 4.1 ship. The behavioral gate (feedback → critical_rules promotion) does not depend on transcript_chunk reach. The mechanical gate (SC#3 ≥80% MEMORY.md content quality) does not depend on transcript_chunks either — they're consumed by future Experience Tier matching (Phase 6.5), not by MEMORY.md curation.

## Honest assessment

Per the CLAUDEXv3 user rule on honest assessment: **CUR-15 cannot be fully closed in Phase 4.1 scope.** The writer fix is genuine progress (eliminates new occurrences of the 10-digit-second class), but the 107-session enqueue gap is structural — caused by historical sessions that pre-date the enqueue mechanism and by edge-case shutdown paths. Bringing reach to ≥1 chunk/session retroactively requires a backfill mechanism that is its own atomic unit of work and should be planned/sized separately.

The Phase 4.1 success criteria SC#3 (MEMORY.md content quality ≥80%) and SC#4 (one-turn handoff pickup) do not depend on transcript_chunk reach, so this defer does NOT block phase completion.
