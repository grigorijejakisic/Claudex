## V17 mapping decision: SIDECAR FALLBACK USED

Per CONTEXT.md "Claude's Discretion" + Plan 07 Task 2 pre-authorization:

> "If neither path works cleanly, fall back to: store multi_project_count in a sidecar table critical_rules_multi_project_count(rule_id INTEGER PRIMARY KEY, count INTEGER NOT NULL) and have the scorer LEFT JOIN it."

**Decision:** sidecar table `critical_rules_multi_project (project, normalized_rule_text, multi_project_count, updated_at_epoch)` keyed by project + normalized text. Reasons:
- V17 critical_rules view does NOT expose `data` JSON column directly; INSTEAD OF triggers don't cover data-level UPDATE
- Direct `UPDATE artifact SET data = json_set(...)` works only when the V17 runner has installed the views (production), not in pre-V17 test environments where critical_rules is a real legacy table
- Sidecar approach is identical in both environments, simpler test fixtures, no V17-runner dependency

Sidecar shape: `(project TEXT, normalized_rule_text TEXT, multi_project_count INTEGER, updated_at_epoch INTEGER, PRIMARY KEY(project, normalized_rule_text))` + index on `normalized_rule_text` for cross-project lookups.

## Sidecar fallback used? **YES.** Documented above.
