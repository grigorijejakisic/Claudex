<axiom>
## Generative Axiom (the design north-star)

This phase is governed by one principle, derived conversationally during the 2026-04-28 design session:

**Experience is a bound multi-modal record. Retrieval fires on perceptual handles, not query strings. Abstraction emerges from density. Encoding density matches experience salience.**

The kid-stove formulation: a child who burns its hand on a stove doesn't store "rule: hot = bad." It stores the bound episode — color, heat, pain, mamma's words — and at recall time *any one* of those modalities can trigger the whole memory. Over many episodes, the kid generalizes: "stove burns" → "hot things burn." The kid becomes "expert" through repetition.

Every Phase 4.1 design decision traces back to one of four claims:
1. **Bound multi-modal episodes** — lessons are not rules; they're records with multiple retrieval handles
2. **Perceptual handles fire retrieval** — match on tools used / files touched / framing language / shape, not on tags or queries
3. **Density-driven abstraction** — Angel watches what recurs and promotes patterns from candidate to canonical
4. **Encoding density matches salience** — rich encoding when surprised / corrected / novel; sparse encoding when routine

Where the metaphor doesn't apply (mechanical schema decisions, bug investigations), the decision is purely engineering judgment.

</axiom>

<domain>
## Phase Boundary

This phase delivers six things and only these six things:

1. **Three lesson file types** with frontmatter schema: `feedback_*` (rules), `project_*` (decisions/facts), `process_*` (decision trajectories)
2. **Layered storage in each lesson file**: narrative-shape body + auto-harvested telemetry handles + bounded-vocabulary shape handles (LLM-extracted, abstain-allowed)
3. **MEMORY.md structural redesign**: managed/user-notes hash boundary; foreground/background tier with promotion-demotion (no hard cap, attention-budget-based); drop `## Entities` and `## Recent Threads` sections; add `## Lessons`; promote `## User Notes`
4. **Vocabulary growth protocol**: Angel curates a shape vocabulary by candidate→canonical promotion at density ≥3; bounded vocabulary, abstain permitted
5. **Trajectory preservation**: `process_*` lesson type with 2-of-5 salience trigger; `transcript_chunk` reach root-cause investigation and fix
6. **`feedback_*` → `critical_rules` promotion bridge** (Architecture B): Angel detects `feedback_*` density within a project, promotes into existing `critical_rules` table with `source='system-promoted'`; existing Critical Reminders Tier consumes the new input source automatically; `multi_project_count` column added with flat +2 scoring boost when ≥2 projects share a promoted rule

**Explicitly out of scope for this phase (deferred):**
- Experience Tier scorer for `project_*` and `process_*` lessons (Phase 6.5)
- Anticipatory retrieval at PreToolUse for context lessons — only rules use it today (Phase 6.5)
- Cross-project pattern matching for un-promoted feedback files (Phase 6.5)
- Embedding-based content-equivalence detection across projects (Phase 6.5)
- Hierarchy-as-view rendering (deferred indefinitely; ship if and when curation surface demands it)
- Tiered cross-project boost (1/2/3-project gradients) — flat boost only in 4.1 (Phase 6.5 refinement)
- Global-scoped `critical_rules` promotion (project='*') (Phase 6.5)
- Cross-encoder reranker changes — Phase 4.1 does not touch the reranker pipeline

**Hard gates:**
- Existing Critical Reminders Tier behavior must be preserved unchanged on rule injection paths
- User-authored MEMORY.md content (Lacuna/Oracle/Nexus and any other project with manual MEMORY.md) must be preserved byte-for-byte; auto-managed sections append above the hash marker, never below
- Substrate must be schema-compatible with the existing `assembleCriticalReminders` scorer (`src/intelligence/critical-reminders.ts`) — Phase 4.1 extends inputs to that scorer, does not replace it

<decisions>
## Implementation Decisions

### Lesson types

Three types only. Curator picks at write time based on content shape:

- **`feedback_*`** — behavioral rules ("WebSocket not polling", "always check existing dependencies"). Distillation of mamma's words. Promotable to `critical_rules`.
- **`project_*`** — factual decisions, root causes, architectural facts ("Mozzart 429 is per-IP, 15-min auto-heal"). Episodic but stable. Not promotable to rules.
- **`process_*`** — decision trajectories with rejected alternatives, probe questions, anti-patterns surfaced. Salience-gated; not every session produces one. Substrate for v5+ meta-design work.

### Layered storage

Every lesson file has the same outer shape; differs only in body length and trigger.

```yaml
---
type: feedback | project | process
created_at_epoch: <ms>
telemetry:                            # auto-harvested, always present, deterministic
  tools_used: [Read, Grep, Bash]
  files_touched: [.planning/audits/*]
  errors_encountered: []
  user_framing_tokens: [audit, design, taxonomy]
  session_arc: [audit, diagnosis, design]
  duration_min: 90
  correction_count: 2
shape:                                # LLM-extracted, optional, bounded vocabulary
  task_shape: design-discussion-before-commit       # confidence: 0.91
  failure_mode: false-framing-corrected             # confidence: 0.84
  solution_pattern: layered-combination             # confidence: 0.78
  # absent fields = no high-confidence vocabulary match → abstain (NOT guess)
---

<narrative-shape salience body — short for feedback/project, longer for process>
```

- Telemetry handles are load-bearing (always present, deterministic, harvested from session telemetry)
- Shape handles are additive (optional, abstain-allowed, drawn from Angel-curated bounded vocabulary)
- Narrative body is the matchable signal — embedding-over-salience is the primary retrieval mechanic

### Vocabulary growth protocol

- Shape handles draw from a bounded vocabulary maintained by Angel
- New candidate shapes go to a candidate pool when LLM proposes a value not in the canonical vocabulary
- Angel promotes candidate → canonical after **density ≥3** (3 sessions independently producing the same candidate shape)
- LLM is permitted (encouraged) to leave `shape` fields blank when no canonical match has high confidence
- Vocabulary lives in a new table `shape_vocabulary` (canonical) + `shape_candidates` (pending) — exact schema is planner discretion

### MEMORY.md structural redesign

**Drop**:
- `## Entities` (frequency-extraction noise — `entity:-`, `entity:--2--1` are visible regressions)
- `## Recent Threads` (50% of entries are session-IDs masquerading as topics)

**Add**:
- `## Lessons` — pointer-line index to lesson files in the project's memory directory; foreground/background tier (see below)

**Promote**:
- `## User Notes` — keep as-is, structurally; the user-authored manual MEMORY.md style in Lacuna/Oracle/Nexus is the gold standard for pointer-line shape

**Hash boundary** (extends existing `<!-- CLAUDEX-MANAGED -->` sentinel):
- Managed sections (above the marker): `## Lessons`, any auto-managed metadata
- User-authored sections (below the marker): `## User Notes` and any user-added content
- Auto-writers must NEVER cross the marker downward
- User edits below the marker must NEVER trigger hash recalculation of managed content
- Existing missing-sentinel rule applies: refuse write and log on corruption

**Foreground/background tier in `## Lessons`**:
- No hard count cap — foreground is bounded by attention budget, not entry count
- Default cap: foreground ≤20 pointer lines, background unbounded
- Promotion: lesson fires (via either CR Tier injection or future Experience Tier match) → moves to foreground
- Demotion: lesson hasn't fired in N=8 weeks → demoted to background tier (still on disk, still searchable, not in always-loaded index)
- Pointer-line cap: ≤140 chars (planner discretion on exact format)

### `process_*` salience triggers (when does Angel propose a trajectory file)

Five candidate triggers:
1. ≥2 corrections in a session (the "ouch" signal)
2. User probe broke a false framing the agent had committed to (mamma's intervention)
3. Decision spanned ≥3 pivots before resolving (effortful binding)
4. A novel pattern fired that's not yet in the shape vocabulary (novelty)
5. Long-form design discussion >30 min, conversation-shaped not action-shaped

**Rule: 2-of-5 must fire, max 1 `process_*` per session, plus explicit override flag.**

- 2-of-5 ensures multi-dimensional salience (surprise alone or effort alone is insufficient)
- Max-1-per-session prevents fragmenting one rich session into multiple thin files; if 4 triggers fire, write ONE comprehensive trajectory
- Explicit override at `/endsession` lets user or agent flag "this matters, save trajectory" — handles edge cases the rule misses
- Threshold (2-of-5) is conservative-by-default and tunable from telemetry

### `feedback_*` → `critical_rules` promotion bridge

**Density**: 3 instances of equivalent `feedback_*` content within a single project triggers promotion.

**Equivalence (in 4.1)**: simple normalized text equality on rule_text — lowercase, strip punctuation, trim whitespace. Embedding-based similarity is a Phase 6.5 enhancement.

**Scope**: project-scoped only in 4.1. If user gives same feedback in 3 separate projects, each promotes locally — slight redundancy, no behavioral incorrectness. Cross-project escalation deferred to 6.5.

**Mechanism**:
- Angel watches `feedback_*` writes
- After local density 3, INSERT row into `critical_rules` with `source='system-promoted'`, drift_risk inferred (working-method default; safety if SAFETY_KEYWORDS hit; style fallback), base_ttl=8 (matches existing system-promoted convention)
- Existing `assembleCriticalReminders` consumes new rows automatically — no scorer changes for the basic path

### Multi-project marker

**New column on `critical_rules`**: `multi_project_count INTEGER DEFAULT 1`

**Update**: Angel heartbeat task runs cross-project SELECT to count distinct projects with similar rule_text (using the same simple text-equality function as the equivalence check). Updates `multi_project_count` for all `source='system-promoted'` rules.

**CR Tier scoring boost**: `+2` to existing scoring when `multi_project_count >= 2`. Flat boost (not tiered).

**Decay**: heartbeat update reflects current state — if a rule is demoted in some projects (existing `promoteFromCapabilityTracker` correction-rate <15% demotion), `multi_project_count` drops naturally on next pass. Boost drops automatically.

### Mechanical schema decisions

**`created_at_epoch` canonical unit: epoch-ms (Date.now() output).**
- Read-time normalization for legacy 10-digit-second rows: `epoch_ms = value < 1e12 ? value * 1000 : value`
- Fix the writer producing 10-digit-second rows in `transcript_chunk` (likely related to low-reach finding)
- No data migration; read-time normalization is reversible and cheap
- Leave `updated_at` TEXT ISO8601 columns as-is — semantically distinct (human audit), not in retrieval hot paths
- ISO8601 reserved for human-facing surfaces only (display, log lines, CLI output)

**No changes needed in `src/intelligence/critical-reminders.ts`** — its decay logic is turn-based, not timestamp-based; `datetime('now')` usage is restricted to `updated_at` audit columns

### Reach mechanism

**Event-driven, not heartbeat-driven for retrieval.**

- PreToolUse, UserPromptSubmit, tool error → potential trigger points for retrieval/injection (but actual injection mechanism for lessons is 6.5; 4.1 ships substrate with handles compatible with these triggers)
- Heartbeat sweeps remain for housekeeping only (vocabulary promotion, demotion, decay, multi_project_count update) — never for retrieval

### Migration policy for existing user-authored MEMORY.md

**Never overwrite. Append above hash marker.**

- Lacuna-Betting, Oracle, Nexus and any other project with manual MEMORY.md content: existing content is **preserved verbatim** below the `<!-- USER EDITABLE -->` marker (or wrapped into `## User Notes` if no marker exists yet)
- Auto-managed sections (`## Lessons`) inserted above the hash marker
- First-run migration logic detects "this project has user-authored MEMORY.md without our markers" and wraps existing content into the user section before adding any managed content

### Investigation deliverables (NOT design — to be done during plan execution)

These are noted as required deliverables of Phase 4.1 plan execution, not design decisions:

- **`transcript_chunk` low-reach root cause** (Audit T3 finding: 20 chunks total in DB). Likely connected to the 10-digit-second timestamp bug — recency-weighted retrieval would silently misorder transcript_chunks against ms-precision peers. Investigate together with epoch normalization.
- **Writer state-machine duplicate-marker bug** (visible regression — duplicate `<!-- CLAUDEX-MANAGED -->` markers). Root-cause analysis required before redesigning writer behavior. Don't bolt fixes on without understanding.

### Live-fire gate split (SC#3 + Phase 4.1 behavioral gate)

**4.1 mechanical gate (SC#3 already locked)**: MEMORY.md content quality ≥80%
- All lesson files have valid frontmatter (telemetry handles populated; shape handles either populated or explicitly blank)
- No `entity:-` style noise
- Hash boundary respected (managed/user sections never cross)
- Pointer-line format consistent

**4.1 behavioral gate**: feedback → rule promotion fires end-to-end
- Probe: write 3 instances of an equivalent `feedback_*` lesson across 3 sessions; trigger Angel's promotion check; verify row appears in `critical_rules` with correct fields; verify `assembleCriticalReminders` returns it under appropriate domain match; verify TTL decay behavior on subsequent sessions
- Plus multi-project marker: write same feedback in 2 projects, verify `multi_project_count=2` after heartbeat, verify +2 scoring boost in CR Tier output
- Pass criteria: ≥80% of probe assertions hold

**4.1 substrate-validation (probe set authored, runs as unit tests)**:
- Author the 6.5 perceptual-similarity probe set (the canonical shadowban example and N variants) as part of substrate work
- Run as unit tests on the substrate: do telemetry+shape handles encode such that 6.5's matcher *would* find the right lesson?
- Substrate validation only — actual perceptual-similarity recall test is Phase 6.5's gate

**6.5 behavioral gate (deferred, listed here for visibility)**: perceptual-similarity probe surfaces lesson via Experience Tier
- Probe set authored in 4.1 hands forward to 6.5
- Pass: ≥80% of probe set surfaces correct lesson in agent context with zero lexical surface overlap on key terms

### Claude's Discretion (planner free to decide)

- Exact filename/slug convention for `feedback_*` / `project_*` / `process_*` (e.g., `feedback_check_dependencies.md` vs `feedback_check-dependencies.md` — slug separator)

- File-write atomicity mechanism (rename(2)-style temp-file swap or fcntl lock)
- Concrete SQL query shapes for new bridge code paths
- Schema layout for `shape_vocabulary` and `shape_candidates` tables
- Whether candidate-shape promotion runs on heartbeat or at `/endsession` boundary

<specifics>
## Specific Ideas

### Architecture B: parallel tiers, shared infrastructure

- Critical Reminders Tier (rules — exists today): scoring on drift_risk × turn-decay × first-encounter × domain match
- Experience Tier (episodes — `project_*` and `process_*`, builds in Phase 6.5): scoring on handle overlap × turn-decay × recency × salience
- Shared: turn-based TTL/decay, Leitner advance/reset, variant rotation, budget cap pattern, deterministic-jitter pattern
- Different inputs, different triggers, different budgets — no competition between rule and lesson injection
- Rationale for B over unified scorer (A): budget collision between rules and lessons + scoring signal blur are real failure modes that B avoids cleanly at the cost of two tier modules instead of one

### `feedback_*` lessons ARE rules in shape

- The bridge promoting `feedback_*` into `critical_rules` is not adding new mechanism — it's recognizing that `feedback_*` lessons are structurally rules and feeding them into the existing rule pipeline
- Avoids parallel infrastructure for the same semantic shape

### Reuse the system-promotion pattern

The existing `promoteFromCapabilityTracker` mechanism (capability_tracker → critical_rules system-promotion at correction-rate threshold, with demotion at <15%) is the same pattern as `feedback_*` → `critical_rules` system-promotion at density threshold. Phase 4.1 should reuse the existing path:
- Same `source='system-promoted'` discriminator
- Same demotion logic (correction-rate based, runs in same pass)
- Same cap convention (max system-promoted rules per project — currently 10 in `promoteFromCapabilityTracker`; planner may extend)

### Substrate compatibility with shipping scorer (not 6.5-only)

A core insight from the design discussion: `src/intelligence/critical-reminders.ts` is already a working anticipatory-retrieval scorer for rules. Phase 4.1's substrate is *not* "data shape that 6.5 will use later" — it's "data shape compatible with a scorer that runs today, plus a bridge to feed it." This makes Phase 4.1 producer-of-a-working-improvement, not pure-substrate.

### Encoding-density-matches-salience as a budget principle

Rich encoding is expensive (LLM cycles, disk space, retrieval-time noise). The 2-of-5 trigger rule, the abstain-allowed shape handles, and the foreground/background tier all enforce: encode richly only when there is salience. Routine sessions get sparse encoding by design — that's not a gap, it's the principle in action.

### Telemetry handles are deterministic; shape handles are not

This is intentional. Telemetry is observable from session state and produces stable handles. Shape is LLM-extracted and produces semantic handles that can drift. The two cover surface and abstraction respectively. Neither is sufficient alone; both add value at different cost levels. Telemetry is required (substrate); shape is optional (additive).

### Live-fire gate is behavioral, not structural

Phase 4 shipped MEMORY.md with structural validation passing while content was visibly broken (`entity:-`, `entity:--2--1`, duplicate markers). Phase 4.1 explicitly avoids this failure mode: the behavioral gate (feedback→rule fires end-to-end) requires the system to actually do something different in production, not just produce schema-valid output.

</specifics>

<deferred>
## Deferred Ideas

- **Experience Tier scorer for `project_*` and `process_*`** — Phase 6.5. Requires perceptual-similarity matching infrastructure across handles and shape vocabulary; bigger surface than 4.1.
- **Anticipatory retrieval for context lessons at PreToolUse / UserPromptSubmit** — Phase 6.5. Today only rules anticipate; lessons require Experience Tier first.
- **Cross-project pattern matching across un-promoted feedback files** — Phase 6.5. Captures the gap where user gives same feedback in 3 projects without any hitting density 3 locally. Requires content-equivalence detection across project memory directories.
- **Embedding-based content equivalence** — Phase 6.5. 4.1 uses simple normalized text equality; embedding-based similarity is more robust but heavier.
- **Tiered cross-project boost (1/2/3-project gradient)** — Phase 6.5 refinement. 4.1 ships flat +2 for ≥2 projects; tiered needs telemetry to tune which we don't have yet.
- **Global-scoped `critical_rules` promotion (`project='*'`)** — Phase 6.5. Cross-project escalation is downstream of cross-project content equivalence.
- **Hierarchy-as-view rendering (`scraping/rate-limits` tree)** — deferred indefinitely. May ship if curation surface demands it; not on the v4 critical path.
- **LLM-generated variant pool for `system-promoted` rule phrasings** — planner discretion or later phase. 4.1 inherits CR Tier's existing variant rotation (rotate stored variants by injection_count); extending the variant pool is independent.
- **Telemetry-handle-based equivalence for un-promoted feedback** — considered for 4.1 inclusion (lighter-weight version of cross-project signal). Declined: doing it half-right in 4.1 (telemetry-only, no shape, no embedding fallback) creates a partial mechanism that 6.5 has to rebuild or graft. Cleaner to design once in 6.5.

</deferred>
