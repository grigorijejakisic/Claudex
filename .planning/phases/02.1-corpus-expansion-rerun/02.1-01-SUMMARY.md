# Phase 2.1 Plan 01: Three-tier corpus_origin partition

Widen the V26 sidecar's `corpus_origin` enum from Phase 2's two tiers (`phase1_organic` / `v4_backfill`) to Phase 2.1's phase-anchored three-tier scheme (CONTEXT.md decision 1c).

**Duration:** 8 min  **Completed:** 2026-05-05  **Tasks:** 4  **Files modified:** 11 (1 new test)

## What changed

- **Type widening:** `CorpusOrigin` is now `'v4_backfill' | 'phase1_organic_pre_phase2_close' | 'phase1_organic_post_phase2_close'`. The boundary `PHASE2_CLOSE_TS_EPOCH=1777940002` is exported from `types.ts` and sourced verbatim from `02-results.json` `harness.ts_epoch`.
- **Pure classifier:** `classifyCorpusOrigin(provenance, ts_epoch)` in `backfill.ts` — non-organic provenance maps to `v4_backfill` regardless of timestamp; organic rows split at the boundary (inclusive on the pre-side per JSDoc).
- **Backfill rewire:** the organic path now passes the per-row classifier result through `SIDECAR_DELETE_BY_EVENT` + `SIDECAR_INSERT`. The v4 path stays at `v4_backfill`. End-of-run logs the per-tier sidecar counts (descriptive, not gating).
- **HarnessRunResult schema:** `metrics.phase1_organic` and `deltas.phase1_organic` renamed to `phase1_organic_pre_phase2_close`; new `phase1_organic_post_phase2_close` keys added at the same level. `corpus_size` carries all three counts.
- **V26→V27 migration:** SQLite has no `ALTER TABLE ... DROP CHECK`, so the migration renames the legacy table, recreates with the relaxed CHECK constraint accepting all three values, copies rows mapping `'phase1_organic'` → `'phase1_organic_pre_phase2_close'`, and drops the rename. `TARGET_USER_VERSION` bumped to 27.
- **Tests:** new `backfill-corpus-origin.test.ts` covers 5 direct classifier cases + 3 integration cases (boundary classification, no-fall-through invariant, content-level idempotency on re-run). Existing tests updated where they hardcoded the legacy literal.

The post-phase-2-close tier is empty — confirmation of CONTEXT.md decision 1a's caveat that 1a alone is supplementary; the labeler relaxation in Plan 02.1-02 is the primary lever for n growth.

## HarnessRunResult shape: forward-only rename

Phase 2's existing `02-results.json` retains its old `phase1_organic` keys on disk — that file is append-only (CONTEXT.md decision 4d). The aggregator in Plan 02.1-04 (`buildPhase2Entry`) handles it as untyped data. Phase 2.1's runner produces the new three-tier shape from this plan onward.
