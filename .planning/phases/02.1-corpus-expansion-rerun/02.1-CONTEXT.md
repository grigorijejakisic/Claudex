<decisions>
## Implementation Decisions

### 1. Corpus expansion strategy (Area 1)

**1a. v4 backfill window — same as Phase 2 + post-Phase-2-close organic only.**
Phase 2.1 uses the SAME v4 `artifact` backfill window as Phase 2 (no extension further back) PLUS any new organic `tool_result` rows accumulated since Phase 2's measurement timestamp (~2026-05-04 23:30) across the active project set. Pure corpus-size delta is the cleanest experimental condition; extending the v4 window would introduce a confounding variable (old vs recent error patterns) on top of the size delta we're testing.

**Caveat — flagged for future readers:** Phase 2's bottleneck wasn't fingerprinted episode count (135 episodes / 10,678 sidecar rows is ample). The bottleneck was the *strict pair-labeler*. Five days of post-Phase-2 organic adds at most ~10–20 fingerprinted episodes (most sessions don't produce errors). Option 1a alone will NOT take held-out pairs from 20 → 200. The labeler relaxation in Area 2 IS the primary lever; corpus expansion via 1a is supplementary. PLAN.md and RESULTS.md must make this explicit so future readers don't attribute the n delta to corpus expansion alone.

**1b. Project diversity floor — keep Phase 2's ≥3 project floor.**
Don't move goalposts. RESULTS.md describes the per-tier project distribution descriptively (no minimum enforced beyond the existing ≥3); raising the floor to ≥5 would be a goalpost shift mid-stream.

**1c. Three-tier `corpus_origin` tagging — phase-boundary anchored.**
Replace Phase 2's two-tier scheme with three tiers, anchored to phase-close timestamps (NOT wall-clock dates) so re-runs remain meaningful:
- `v4_backfill` — unchanged from Phase 2
- `phase1_organic_pre_phase2_close` — Phase 1 organic accumulated up to Phase 2's measurement timestamp (~2026-05-04 23:30)
- `phase1_organic_post_phase2_close` — everything organic accumulated after Phase 2 closed

Reason for phase-anchoring: if we re-run 2.1 in a week, the partition stays meaningful. Date-anchored tags would require re-stamping, breaking the bound-experience invariant.

**Combined RESULTS.md reporting:** every metric reported four ways per tier — pooled, by `v4_backfill` only, by `phase1_organic_pre_phase2_close` only, by `phase1_organic_post_phase2_close` only. If the post-phase-2-close organic slice trends differently from the pre-phase-2 slice, that itself is an interesting bound-experience signal (organic capture quality may have shifted post-Phase-1 ship).

### 2. Pair-labeler — threshold-tested, two parallel labelers (Area 2)

**2a. Threshold-tested strategy: run BOTH strict and relaxed labelers independently.**
Not a fallback. Two bound experiences > one.
- Strict labeler: same outermost exception type + ≥3 frames overlap + different `session_id` (Phase 2's labeler verbatim)
- Relaxed labeler: same outermost exception type + ≥2 frames overlap + different `session_id`

Both run on the same fingerprint corpus. Each produces its own held-out test set. **The locked decision rule from Phase 2 CONTEXT.md item 5 is applied INDEPENDENTLY to each tier.** The verdict module runs twice. RESULTS.md reports two parallel verdicts:

> "at strict (≥3 frames) labeler, n=X, verdict V1, with auto-labeler precision P1/20, conditions={...}"
> "at relaxed (≥2 frames) labeler, n=Y, verdict V2, with auto-labeler precision P2/20, conditions={...}"

There is **NO combined-into-one verdict.** No "winning" tier, no "primary" verdict. If the two tiers disagree, both stand — disagreement IS the bound-experience finding ("verdict is sensitive to labeler strictness"). The aggregating reader (orchestrator + user) integrates across all bound experiences; the phase does not compress.

**2b. Floor on relaxation: ≥2 is hard floor; never go below.**
The roadmap permits ≥2; ≥1 is too noisy a signal — same exception type + one shared frame is a coincidence rate the auto-labeler can't reliably distinguish from genuine match. If even ≥2 doesn't reach n=200, that itself is a bound experience worth reporting honestly: "at our scale, even relaxed labeling produces n=X<200 — corpus is too sparse for the held-out methodology at the requested precision." The corpus-too-sparse finding becomes the primary outcome, not a problem to engineer around. Methodological honesty over hitting a number.

**2c. Both labelers always run, regardless of strict's n.** (Follows from 2a.) If strict alone reaches n=200, we still run relaxed — two bound experiences, not one. If strict doesn't reach n=200, we report what it reached and run relaxed in parallel.

**2d. 20 spot-checks per tier, stratified.** (See Area 3.)

**Verdict-module discipline (binding for the planner):**
- The existing `runVerdict(harness_results, decision_rule) → verdict_object` interface is unchanged.
- Phase 2.1's runner calls it exactly twice with two different `harness_results` inputs (strict tier, relaxed tier).
- 02.1-04 PLAN must include an ordering test asserting `runVerdict` is called exactly twice with distinct labeler inputs.
- 02.1-results.json has two top-level verdict objects. NO `combined`, `winning`, or `primary` key. Schema test asserts this.

### 3. Manual spot-check audit — descriptive, agent-run (Area 3)

**3a. Sampling: 20 pairs per tier, stratified proportionally by `corpus_origin`.**
Of 20 pairs per tier, allocation is proportional across the three corpus_origins (e.g., if `v4_backfill` is 60% of the tier's pair set, ~12 of the 20 spot-checks come from `v4_backfill`). Each tier × `corpus_origin` is its own bound experience per Area 1's three-tier structure; stratified sampling is the only way the audit also respects that structure. Stratification by exception type is a planner-discretion nice-to-have; not load-bearing.

**3b. Audit is descriptive, NOT a gate.**
Auto-labeler precision (X/20 valid pairs at this tier × this corpus_origin) becomes a *measured condition* of the bound experience, reported in RESULTS.md alongside n, delta_p5, Wilson CI, etc. It does NOT determine whether the tier "ships" — every tier ships its verdict and its conditions. The locked decision rule (Phase 2 CONTEXT.md item 5, Wilson CI binding) does the only gating.

**Hazard avoided:** tier-specific audit bars (90% / 95%) that change after seeing the data are exactly the moving-goalposts trap the parable rejects. Descriptive-only removes the temptation entirely.

Per-tier RESULTS.md entry shape:
> "verdict V at tier T (≥X frames), n=N, with auto-labeler precision P/20 (P_v4 from v4_backfill, P_pre from phase1_organic_pre_phase2_close, P_post from phase1_organic_post_phase2_close), with metrics={...}"

**3c. Auditor: full agent autonomy. The phase executor agent does the audit.**
No user-review gate at the audit artifact. Reasoning:
- Autonomous-pipeline mode is the operating constraint; inserting a user-review gate at every empirical phase's audit violates that intent.
- 3b makes the audit descriptive-not-gating; agent-judges-agent circularity matters far less when the audit doesn't gate the result.
- The audit artifact is a permanent record. If a future operator wants to manually re-audit, the artifact gives them the pair list. No live-session interruption needed.
- Phase 2's `02-03-corpus-audit.md` was agent-produced and worked clean.

If autonomous mode flips later, this can be revisited.

**3d. Audit and verdict run in parallel** (no abort logic, since audit is descriptive).
RESULTS.md joins audit precision figures with verdict outputs after both complete.

**Two audit artifacts ship per phase:**
- `02.1-XX-strict-audit.md`
- `02.1-XX-relaxed-audit.md`

Both descriptive, both stratified-by-corpus_origin. If the relaxed labeler returns n<200, its audit is still produced and published — the corpus-too-sparse finding lives alongside the descriptive precision figure for that tier. Naming convention is planner discretion; the suggestion above is for clarity.

### 4. Reporting shape — per-phase + milestone aggregating layer (Area 4)

**4a. File layout: BOTH per-phase RESULTS + milestone-level aggregator.**

Per-phase deliverable (roadmap-named, self-contained for cold reading):
- `.planning/phases/02.1-corpus-expansion-rerun/02.1-RESULTS.md`
- `.planning/phases/02.1-corpus-expansion-rerun/02.1-results.json`

Milestone-level aggregator (NEW pattern, durable across phases):
- `.planning/aggregates/multi-handle.md`
- `.planning/aggregates/multi-handle.json`

Naming rationale: `aggregates/` (NOT `RESULTS-multi-handle-thesis.md`) because "thesis" implies pass/fail framing the parable rejects; `aggregates/` is parable-aligned and the directory pattern is reusable. Future empirical phases that touch other questions add their own aggregator (e.g., Phase 5's bound experiences about density-based abstraction land at `.planning/aggregates/density-abstraction.{md,json}`). One `.md` + one `.json` per empirical question is the documented pattern.

The aggregating files are seeded at 02.1 close with Phase 2's existing verdict (re-quoted from `02-results.json`) plus Phase 2.1's two new entries (strict + relaxed).

**4b. Verdict ordering / framing in the aggregate: BOTH chronological table primary AND verdict-grouping summary below.**

Primary: chronological table — one row per bound experience: phase, date, labeler, n, delta_p5, Wilson CI, latency p99 ratio, intra-project share, verdict, full conditions block.

Below: verdict-grouping summary — counts of bound experiences in GREEN / SCOPE-DOWN / KILL groups. Cold reader sees emerging consistency-of-failure or consistency-of-success at a glance.

**4c. Aggregate-level interpretive language: description + emerging-pattern paragraph in density-language**, with three discipline rules:

1. **Density-language only.** Permitted phrasings: "N bound experiences, M with verdict V", "density of consistent X / mixed", "no abstraction yet at this density of evidence", "more measurements needed before milestone-level claim". **Forbidden phrasings:** "the thesis works/doesn't work", "fusion is/isn't justified", any single-experience generalization, "Phase 3 ships / does not ship".

2. **No action-conditional language.** No "if N=200 lands GREEN then Phase 3 ships". The paragraph describes; it does not prescribe next steps. Next steps are owned by the orchestrator + user reading the aggregate, not by the aggregate doc itself.

3. **The interpretive paragraph is append-evolving, not rewritten.** Each phase that ships PREPENDS a new dated section to the aggregator's interpretive paragraph; prior content remains. The aggregator's history is itself a bound experience — readers see how the synthesis evolved as more measurements landed. Rewriting prior interpretive paragraphs is forbidden.

**4d. JSON schema: per-phase JSON self-contained + milestone aggregator append-only event-sourced.**

`02.1-results.json` contains only Phase 2.1's two verdicts. Phase 2's `02-results.json` is unchanged.

Milestone aggregator at `.planning/aggregates/multi-handle.json` is **strictly append-only event-sourced**:

```json
{
  "question": "does multi-handle retrieval (semantic + non-semantic) improve recall over semantic-only at our scale?",
  "bound_experiences": [
    {"phase": "2", "labeler": "strict_3frame", "date": "2026-05-04", "n": 20, "verdict": "...", "conditions": {...}, "metrics": {...}},
    {"phase": "2.1-strict", "labeler": "strict_3frame", "date": "...", "n": "...", "verdict": "...", "conditions": {...}, "metrics": {...}},
    {"phase": "2.1-relaxed", "labeler": "relaxed_2frame", "date": "...", "n": "...", "verdict": "...", "conditions": {...}, "metrics": {...}}
  ]
}
```

Schema rules (binding for planner; will be enforced via test in 02.1-04):
- Existing entries are NEVER modified. Each phase appends exactly the entries it produced — Phase 2.1 appends two (strict + relaxed) at close.
- New empirical phases append theirs in turn. The array length over time IS the density measurement.
- NO `winning` or `current_consensus` key at the top level. Aggregate IS the array; consumers iterate.
- Schema is forward-compatible: adding new fields to `conditions` or `metrics` per-entry is fine; renaming/removing fields breaks the parable invariant (history must remain readable as written).

This matches the v5 framing doc's "raw transcripts append-only; synthesis is a projection" principle applied to our own engineering process. The markdown aggregator's append-only paragraph history (per 4c rule 3) is the human-readable projection over the JSON event log.

### 5. Locked decision rule — REUSED VERBATIM from Phase 2 CONTEXT.md item 5

No moving goalposts. The Wilson/Newcombe CI binding is non-negotiable. Reproduced here for the planner's reference; the verdict module already implements it.

**GREEN-LIGHT verdict — ALL three must hold on the held-out test set:**
1. RRF-fusion has measurable improvement over semantic-only — minimum **+5pp on either precision@5 OR recall@10**, AND the **Wilson 95% CI lower bound on the delta is ≥ 0**.
2. Density at scale produces signal — ≥30% of high-similarity pairs (per Phase 2 CONTEXT item 4) are intra-project recurrent.
3. Latency p99 of fused retrieval < 2× semantic-only baseline.

**SCOPE-DOWN to advisory:** improvement exists on specific subsets (e.g., one project, one exception type) but not broadly.

**KILL:** no measurable improvement (criterion 1 fails on held-out CI bound) OR density is pure noise (criterion 2 fails).

This rule is applied INDEPENDENTLY to each tier per Area 2. Two verdicts; no combination.

### 6. Outcomes language — descriptive of conditions, NOT thesis-claims

Whichever way 2.1 lands, the language in RESULTS.md and the aggregator stays descriptive of conditions, not generalizing to thesis claims:

- **GREEN-LIGHT verdict at n≥200 (any tier):** "Phase 2.1 [tier] cleared the locked decision rule's bar at n=X. Combined with Phase 2's KILL at n=20, the aggregator now contains [N] bound experiences with [breakdown by verdict]. Per the parable, density of [...] at this evidence level [...]." Phase 3 readiness is NOT a function of 2.1 alone — orchestrator + user decide at the next user-approval gate, looking at the aggregator.
- **KILL verdict at n≥200 (any tier):** "Phase 2.1 [tier] failed criterion [N] at n=X (CI lower bound, intra-project share, etc.). Combined with Phase 2's KILL at n=20, the aggregator contains TWO bound experiences both with KILL verdicts under different conditions — emerging density of consistent failure. This is much stronger evidence to escalate at milestone level than any single measurement." (NOT: "the thesis is dead.")
- **Mixed (e.g., strict GREEN, relaxed KILL):** "Phase 2.1 strict cleared the bar; Phase 2.1 relaxed did not. Verdict is sensitive to labeler strictness — itself a finding about the methodology. Aggregator contains three bound experiences with mixed verdicts."
- **n<200 even at relaxed:** "Even relaxed labeling produced n=X<200 at this corpus size; corpus is too sparse for the held-out methodology at the requested precision. The corpus-sparsity finding is the primary outcome of this bound experience."

Forbidden language in any output of Phase 2.1: "fusion works", "fusion doesn't work", "the multi-handle thesis is validated/invalidated", "Phase 3 should/should not ship", "this proves/disproves [...]". The locked decision rule's verdict words (GREEN-LIGHT / SCOPE-DOWN / KILL) are permitted as labels of bound-experience verdicts; they MUST NOT be promoted to milestone-level claims.

### 7. Negative-result handling — same as Phase 2

If the aggregator after 2.1 close shows two consistent KILLs:
- Vesna probes stay in `.disabled/` (already there).
- `DEFAULT_CONFIG.features.error_fingerprint` stays `false` (already there).
- Backfill data + sidecar retained — destructive cleanup is not the answer; future re-runs reuse existing index data.
- The aggregator's interpretive paragraph at 02.1 close describes the emerging density of failure in parable language and notes "more bound experiences may be needed before any milestone-level claim is warranted." No phase-level decision to "kill the thesis" — that's a milestone-level action owned by the user.

If the aggregator shows mixed or one consistent GREEN:
- Same artifacts (probes, config flag, backfill) all unchanged at 02.1 close — single GREEN does not ship probes.
- The interpretive paragraph notes the mixed/single-green finding; orchestrator + user decide at the user-approval gate whether more bound experiences are needed before considering Phase 3.
