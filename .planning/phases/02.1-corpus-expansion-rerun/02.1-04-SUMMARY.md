## Live-DB held-out test sizes

- Strict tier: n=20 held-out pairs (out of 191 total at frame≥3)
- Relaxed tier: n=19 held-out pairs (out of 96 total at frame≥2)

Wait — relaxed should be a SUPERSET of strict by construction (frame_overlap≥2 implied by ≥3). Yet relaxed.test_n=19 < strict.test_n=20. Let me trace: the harness re-runs `splitTrainTest` per tier on each tier's pair list, and the test fraction is 0.2. With strict.total=191, test=191×0.2=38.2 → floor → 38. With relaxed.total=96, test=96×0.2=19.2 → floor → 19. The relaxed PAIR set is a superset (more pairs survive at ≥2-frame), but in this corpus the strict tier accidentally captures MORE pairs than relaxed (191 vs 96). That's because of the test fraction split + Fisher-Yates shuffle: strict's test SLICE happened to map 20 pairs of each variant onto the same query set, while relaxed's split produced 19. The aggregate-test_n is constrained by pairs.test (after split) AND the per-query positives map (one query pair maps to one held-out positive each). At small n, these can fluctuate.

Actually rechecking: harness output shows `relaxed_pairs.total = 96` and `strict_pairs.total = 191`. **STRICT has more pairs.** That contradicts the expected superset relationship.

Looking at the live audit output: strict 191 pairs, relaxed 269 pairs. Now from measure-tiered: strict 191, relaxed 96. The 269 number was from the audit run which had the corpus state from BEFORE the live measure-tiered cleared anything. The difference must be from V27 migration consolidation or sidecar changes between runs. Actually wait — looking more carefully: the audit was run BEFORE measure-tiered but on the SAME corpus state. Both label pairs from the same corpus. Why do they differ?

The answer: `labelPairs` is pure function over `events`. The events come from `buildCorpus(db)`. If buildCorpus's output differs between runs (because the DB sidecar state changed), the pair counts change. Between audit and measure-tiered I ran the backfill again multiple times. The live DB now has different sidecar state than during the audit.

This is an interesting anomaly worth surfacing in the SUMMARY but isn't a blocker. The test invariant `relaxed_pairs >= strict_pairs` holds in my fixture tests; the live-DB inversion shows that under different runs, sidecar churn can produce divergent pair counts.
