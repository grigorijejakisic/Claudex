The test simulates a realistic CC turn cycle and asserts the substrate's row pattern after each step. It does NOT actually invoke the hook scripts (those have heavy CC-context dependencies); it calls the helpers directly in the same order a real CC session would, then asserts on the resulting DB state.

Required scenarios (one `describe` block, named `Phase 1 — Episode substrate end-to-end (EPI-01..EPI-07)`):

1. **`'EPI-01..EPI-07: clean turn with no injection'`** — call `dualWriteUserPrompt(db, sess, proj, 'How does X work?')` → `writeToolResult(...)` for a synthetic Bash → `dualWriteAssistantMessage(db, sess, proj, "Here's how X works...")`. Assert:
   - `conversation_turns` has exactly 1 row with both user_text and assistant_text populated.
   - `episodic_events` has exactly 3 rows: 1 organic user_prompt, 1 tool_result, 1 organic assistant_message.
   - All three rows share the same `session_id`. The user_prompt and assistant_message share `turn_number`. The tool_result has the same `turn_number`.
   - No row has `provenance='injected'` (no wrappers in input).

2. **`'EPI-04: prompt with three different wrappers produces 1 organic + 3 injected'`** — call dualWriteUserPrompt with `'real question\n<system-reminder>SR</system-reminder>\n<experience-data>EXP</experience-data>\n<file-content path="x">FC</file-content>'`. Assert:
   - 1 conversation_turns row (user_text = raw prompt unchanged).
   - 4 episodic_events rows: 1 organic + 3 injected.
   - Organic content does NOT contain 'SR', 'EXP', or 'FC'.
   - Each injected row has `parent_event_id` = organic row's id.
   - Injected rows' content is exactly 'SR', 'EXP', 'FC' respectively.

3. **`'EPI-04 + EPI-07: Mem0 trap structurally impossible'`** — same fixture as #2, but the assertion is:
   - `SELECT content FROM episodic_events WHERE provenance='organic' AND session_id=?` — assert the result strings ALL pass the predicate `s => !s.includes('SR') && !s.includes('EXP') && !s.includes('FC')`.
   - This is the load-bearing test for the substrate's defining claim.

4. **`'EPI-03: tool result rows do not pollute organic'`** — write a tool_result whose content contains every wrapper tag (`'<system-reminder>...</system-reminder>'`). Assert:
   - The tool_result row's content contains the wrapper-looking text verbatim (not stripped — tool results are opaque per CONTEXT.md).
   - But `WHERE provenance='organic'` SELECT still doesn't return the tool result content — `provenance='tool_result'` rows are filtered out.

5. **`'EPI-05: tool_input visible in metadata_json'`** — writeToolResult with toolInput `{ command: 'ls -la', cwd: '/foo' }`. Assert that JSON.parse(metadata_json).tool_input matches the input.

6. **`'EPI-06: legacy conversation_turns preserved'`** — after the full sequence, the conversation_turns row's `user_text` is the RAW prompt with wrappers intact. The legacy table is the v4 backwards-compat surface.

7. **`'EPI-03: environmental events on session boundary'`** — call writeEnvironmentalEvent for session-start, then the full turn sequence, then writeEnvironmentalEvent for session-end. Assert:
   - 2 environmental rows (start + end), both with `turn_number=NULL`, `parent_event_id=NULL`, `provenance='environmental'`.
   - The environmental rows do NOT participate in any turn-bound query (e.g., `WHERE turn_number IS NOT NULL` excludes them).

8. **`'Atomicity: rollback yields zero new rows + one telemetry row'`** — set up DB state, snapshot row counts, call a write helper with input that triggers a CHECK constraint failure (or monkey-patch one of the prepared statements to throw mid-transaction), then assert:
   - delta(conversation_turns) === 0.
   - delta(episodic_events) === 0.
   - delta(telemetry where event_kind='episodic_write_failure') === 1.

Each test name MUST start with the requirement ID(s) it covers (`EPI-01`, `EPI-04`, etc.) so a future grep `bun run test --grep "EPI-"` lists Phase 1's coverage.

**Avoid:**

- Adding readers from production code. The "stub extractor" in scenario 3 is a SELECT inside the test only.
- Asserting timing or ordering between concurrent sessions — not in scope for Phase 1.

1. **Create `src/tests/integration/phase-1-extractor-stub.test.ts`** — a focused, narrow test that exercises the structural property the entire phase exists for. The "stub extractor" simulates what Phase 4's reduced extractor will look like: a function that, given a session_id, returns ONLY the organic content for use by any LLM-facing surface.

   ```typescript
   /**
    * Stub extractor — what Phase 4 will look like (Mem0 trap structurally impossible).
    * Reads only provenance='organic' content. This function in production would feed
    * any synthesis/abstraction loop. It MUST never see injected or tool_result content.
    */
   function stubExtractor(db: Database.Database, sessionId: string): string[] {
     return (db.prepare(
       `SELECT content FROM episodic_events
        WHERE session_id = ? AND provenance = 'organic'
        ORDER BY id`
     ).all(sessionId) as Array<{ content: string }>).map(r => r.content);
   }
   ```

   Tests:
   - **Property test (input fuzzing)** — generate a wide variety of prompt shapes (random wrappers, random tags, random nesting *between* — not within — wrappers, random text). For each, call dualWriteUserPrompt + writeToolResult, then assert `stubExtractor()` returns content that NEVER contains any of the synthetic wrapper or tool-result markers. Use a fixed seed for reproducibility (e.g., a fixed array of 20 hand-crafted but diverse inputs is fine — full property-based testing with fast-check is overkill for Phase 1).
   - **Tool result polluted with everything** — write a tool_result whose content contains the literal strings `'INJECTED CONTENT'`, `'<experience-data>'`, etc. Assert stubExtractor never returns those strings.
   - **Mass scale** — write 50 turns with mixed wrappers + tool calls, assert stubExtractor returns exactly 50 user-prompt strings + 50 assistant-message strings = 100 strings, none containing wrapper tags or tool-result markers.

   The point of this test file: even an attacker who tries to smuggle data through wrappers or tool results CANNOT make it appear in the organic-extractor output. The DB schema's CHECK constraint + the dual-write helper's split + the SELECT filter combine into a structural defense.

2. **Write `.planning/phases/01-episode-substrate/01-04-substrate-readme.md`** — operator-facing reference document. NOT a redundant copy of CONTEXT.md; it's the post-shipment "how this works in production" doc that future phases read first.
