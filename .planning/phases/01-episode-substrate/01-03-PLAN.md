   ```typescript
   export interface ToolResultWriteParams {
     db: Database.Database;
     sessionId: string;
     project: string;
     toolName: string;                          // becomes `source`
     toolInput: Record<string, unknown>;        // serialized into metadata_json
     toolResult: string;                        // becomes `content`
     turnNumber?: number;                       // optional; PostToolUse SHOULD pass the current turn
     parentEventId?: number;                    // optional; if the tool call originated from an assistant_message row, link via parent_event_id
   }

   export function writeToolResult(params: ToolResultWriteParams): { episodicId: number | null } {
     // Inside db.transaction:
     //   INSERT INTO episodic_events (
     //     session_id, project, ts_epoch, turn_number, type, source, content, provenance,
     //     parent_event_id, content_hash, metadata_json, schema_version
     //   ) VALUES (?, ?, unixepoch(), ?, 'tool_result', ?, ?, 'tool_result',
     //             ?, ?, ?, 1)
     //   metadata_json = JSON.stringify({ tool_input: params.toolInput })
     //   content_hash = sha256(params.toolResult)
     // On throw → emitTelemetry('episodic_write_failure', { hook: 'post-tool-use', tool: params.toolName, error_message })
     // Returns { episodicId: <inserted id> | null on failure }
   }
   ```

   Notes:
   - `content` is the raw tool result string the agent saw. If the tool's response is a JSON object, JSON.stringify it for `content`. (The CC payload truth doc says PostToolUse uses field name `tool_response`, not `tool_output` — confirm what shape the existing `processToolAndPressure` receives in `lifecycle.ts:216` and use the same convention.)
   - **Do NOT decompose** the tool result into sub-rows. Per CONTEXT.md: "We do NOT decompose recall output into sub-rows — the tool boundary is the natural split."
   - `source` is the literal tool name (`'Bash'`, `'Read'`, `'claudex_search'`, etc.) — NOT prefixed. Phase 2's error-fingerprint index will filter by source.
   - No legacy mirror; tool results were never stored in `conversation_turns`.
   - Single-row write inside its own transaction (`db.transaction(() => insert)()`) — keeps the rollback+telemetry pattern consistent with Plan 02.

   Determine the correct payload field for the tool result text from the existing handler — it's `tool_response` per the project's CC payload truth doc (`.claude/rules/hooks-safety.md`).

   The `turn_number` for the tool result: query the latest `conversation_turns` for that session, like the existing pattern at `user-prompt-submit.ts:425`. Pass it. If no turn exists yet (rare — tool fired before any user prompt), pass NULL.

   The `parentEventId` is OPTIONAL for Phase 1. Linking tool_result rows to the assistant_message row that called them is a convenience for Phase 3 retrieval. For Phase 1, pass NULL — Phase 4 (Angel reduction) revisits this when the tool-call → tool-result chain becomes load-bearing for retrieval.
