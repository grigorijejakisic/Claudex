## 1. Existing surfaces — what we extend, what we leave alone

### 1.1 MCP recall server (`src/mcp/recall-server.ts`)

The single instrumentation point per CONTEXT.md (`<decisions>` block).
Two retrieval-shaped tools to wrap:

- `claudex_search` — registered at line 120; returns RRF-fused hits across
  `artifacts`, `journal`, `conversation_turns`, `learnings`, `decisions`.
  Already constructs an `activeSessionId` (lines 165-178) for telemetry —
  reuse that variable for the new retrieval log row.
- `claudex_recall` — registered at line 560; resolves an artifact by id
  or `artifact_ref`. Already calls `logLessonRecallIfApplicable` (line 593)
  to feed `pointer_recall_log` (Phase 5.5). Phase 8.5 ADDS a sibling call
  to log the broader retrieval event (does not replace pointer log).

Two non-retrieval tools (`claudex_store`, `claudex_session`,
`claudex_curated_context`, `claudex_message`, `claudex_events`) are NOT
instrumented — they don't return content the agent uses for framing.
`claudex_events` is borderline (history readout) but CONTEXT.md scope
limits us to `claudex_search` / `claudex_recall` / pointer-surfacing.

**Pointer-surfacing channel:** `pointer_recall_log` (Phase 5.5) already
captures lesson/user-note recalls via MEMORY.md inclusion. Phase 8.5
does NOT duplicate this — it joins/aggregates on it where needed (the
`used_in_output` overlap heuristic already partially covered by
`pointer_recall_log.helpful_yn` for pointer rows).

### 1.2 Token estimation today

`src/shared/text-utils.ts:53` — `estimateTokens(text)` is `Math.ceil(text.length / 4)`.
**This is not cl100k_base**. It's a rough proxy with ~10-30% drift
on prose, larger drift on code/JSON. CONTEXT.md mandates real tokenizer
counts at the surface ("not estimated").

`gpt-tokenizer` (v3.4.0) is already in `package.json:dependencies`.
We use cl100k_base (Phase 5 token-budget alignment per CONTEXT.md).

**Decision:** introduce `countTokensCl100k(text)` in `src/shared/text-utils.ts`.
Keep `estimateTokens` for non-surface budget gates (no churn risk). Use the
new function ONLY at the three Phase 8.5 surfaces:

1. `retrieval_log.token_cost`
2. `/endsession` summary numbers
3. `/claudex-why` aggregate

Never call cl100k_base on hot paths (per-turn assembly is `estimateTokens`
already and stays that way — switching mid-flight is out of scope).

### 1.4 Self-narration insertion point

CONTEXT.md `<artifacts>` lists `src/intelligence/sections.ts` — that file
does NOT exist (verified). The closest live surface is the assembly
formatter in `src/assembly/assembler.ts` (UPS path) and the framing
formatters under `src/intelligence/`.

For the *agent* to narrate (the OBS-02 requirement), narration is not a
code-side formatter — it is system-prompt-level guidance instructing the
agent to vocalize retrieval. So the insertion is **content, not code**:

- Add a *narration directive* block to the MCP `instructions` payload
  (currently lines 89-105 of `recall-server.ts`). The payload is the
  authoritative system-prompt-level Claudex guidance.
- Add a `/silent` slash command that sets a session-scoped flag in the
  DB (`session_signals` already supports this) which the directive
  references.
- Wire a one-line cue rendered in session-start UPS (or the existing
  Claudex Ready section) when `/silent` is OFF, reminding the agent to
  narrate retrieval moments. This is a sentence, not a section.

The agent narrates during user-facing output. The narration log (token
cost of narration itself) is small and inside the agent's normal
turn-output budget — we do NOT count narration tokens against a separate
budget; it is the agent's voice using the agent's existing turn budget.

## 3. `used_in_output` heuristic — implementation

CONTEXT.md `<decisions>`: ≥2 distinctive tokens from retrieved content
appear in agent output within 5 turns of retrieval → `used_in_output=1`.

Implementation:

- Heuristic runs **at session end** (or at /endsession, whichever fires
  first), not per-turn. Per-turn would require live agent-output capture
  on every assistant turn, which is hot-path cost we don't need.
- Source: `retrieval_log` rows for the session × `transcript_chunk`
  rows (assistant text) for the session.
- Distinctive token = lowercase token of length ≥6 OR length ≥4 if
  it's all-letters and not in a stopword list (top-100 cl100k_base).
- Window: assistant turns 1-5 *after* the retrieval row's
  `invoked_at_epoch_ms`. (Approximate "5 turns" via timestamp ordering
  on `transcript_chunk.timestamp_epoch`.)
- Update `retrieval_log.used_in_output = 1` for matched rows; leave
  `0` for non-matches. Default at INSERT is 0.

Function signature:

```ts
export function reconcileUsedInOutput(
  db: Database,
  sessionId: string,
): { rowsUpdated: number };
```

Run this from:
1. `src/cli/session-token-cost.ts` before reading the rows (so the
   /endsession block reflects accurate hit-rate).
2. The Angel `session-monitor` on idle-close (catches sessions that
   never run /endsession).
3. `src/cli/why.ts` (mid-session view runs reconciliation against
   what's available; some recent retrievals will still have a 5-turn
   window unfilled and stay at 0 — that's accepted false-negative).

## 4. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Cache regression from new MCP `instructions` content | Narration directive is appended to the existing single string. Same string, longer. Cache-stability test (Phase 5 harness) re-runs in the gate plan. |
| Performance hit from cl100k_base on every retrieval | Tokenizer call is one per `claudex_search`/`claudex_recall` call (~10-50ms added to a query that already takes 100s of ms for hybrid + reranker). Acceptable. |
| `top_k_results` JSON blob size | Capped at limit=50 → ~5KB max. Indexed only on `(session_id, invoked_at_epoch_ms DESC)` — JSON column not indexed. Fine. |
| `used_in_output` heuristic over-marking via stopwords | Stopword filter + min-length gate. Acceptance per CONTEXT.md: signal not verdict. |
| `/silent` toggle invisible after set | Step 1c in `/endsession` already inspects session signals; planner adds a one-liner if silent was set. |
| Vesna probes failing on first run because narration is rare | Probes are deterministic against the *directive presence*, not the agent's actual narration content (which is non-deterministic). Probe asserts: "directive block present in instructions output when silent flag is off; absent when on". Optional probe: behavioral spot-check against a known retrieval scenario, asserted via overlap with retrieval result tokens. |

## 5. Suggested wave structure for the planner

CONTEXT.md is silent on plan/wave count. Recommendation:

**Wave 1** (parallel-safe foundations):
- Plan 01: V22 schema + retrieval-log helper module + `countTokensCl100k`
- Plan 02: Narration directive + `/silent` toggle (independent surface)

**Wave 2** (consumers — depend on 01):
- Plan 03: MCP server instrumentation (search + recall callers)

**Wave 3** (CLIs + skill wiring — depend on 03):
- Plan 04: `session-token-cost` CLI + `endsession` skill update +
  `used_in_output` reconciliation
- Plan 05: `why` CLI + `claudex-why` skill

**Wave 4** (gate):
- Plan 06: 2 Vesna probes + cache-stability re-gate +
  STATE/ROADMAP/REQUIREMENTS update + 08.5-SUMMARY.md

This keeps surfaces independent (each plan is one logical concern) and
lets Wave 3 plans run in parallel since they touch disjoint files.

The planner is free to merge or split. The bones of the work are: V22
migration, helper module, MCP instrumentation, two CLIs, skill MDs,
narration directive, two probes.
