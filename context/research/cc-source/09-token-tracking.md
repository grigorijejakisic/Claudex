## 1. How Are Tokens Counted?

### 1.1 The Four Token Types

Every API response carries a `BetaUsage` object (from `@anthropic-ai/sdk/resources/beta/messages/messages.mjs`) with four distinct token fields:

| Field | Meaning |
|-------|---------|
| `input_tokens` | Non-cached input tokens (net new context) |
| `output_tokens` | Tokens generated by the model |
| `cache_read_input_tokens` | Tokens served from the prompt cache (cheap reads) |
| `cache_creation_input_tokens` | Tokens written into the cache (expensive writes) |

There is also `server_tool_use.web_search_requests` for web search billing.

### 1.2 Context Window Size Formula

**File:** `src/utils/tokens.ts`, line 46–53

```typescript
export function getTokenCountFromUsage(usage: Usage): number {
  return (
    usage.input_tokens +
    (usage.cache_creation_input_tokens ?? 0) +
    (usage.cache_read_input_tokens ?? 0) +
    usage.output_tokens
  )
}
```

This is the **full context size** at the time of the API call. All four token types are summed. Cache read + cache write tokens ARE included in the context window size (they represent content that was present in the prompt).

### 1.3 Task Budget / Server-Side Budget Formula

**File:** `src/utils/tokens.ts`, lines 79–112 (`finalContextTokensFromLastResponse`)

For the API-side task budget countdown (see section 4), the formula is different — it **excludes cache tokens**:

```typescript
// Falls back to top-level input_tokens + output_tokens when iterations is absent
return usage.input_tokens + usage.output_tokens
```

When `iterations` is present (server tool loops), it uses `iterations[-1].input_tokens + iterations[-1].output_tokens`. This matches the server-side formula in `api/api/sampling/prompt/renderer.py:292` (`calculate_context_tokens`), which defines the budget countdown. Cache tokens do NOT count toward the task budget countdown.

### 1.4 Rough Estimation (When No API Usage Available)

**File:** `src/services/tokenEstimation.ts`, lines 203–208

```typescript
export function roughTokenCountEstimation(
  content: string,
  bytesPerToken: number = 4,
): number {
  return Math.round(content.length / bytesPerToken)
}
```

Default: **4 bytes per token** (English text). Special case for dense JSON:

```typescript
export function bytesPerTokenForFileType(fileExtension: string): number {
  switch (fileExtension) {
    case 'json':
    case 'jsonl':
    case 'jsonc':
      return 2   // JSON has many single-char tokens
    default:
      return 4
  }
}
```

For images/documents: flat estimate of **2000 tokens** (conservative estimate to avoid under-counting and triggering autocompact too late).

## 2. How the Cost Tracker Works

### 2.1 State Storage

**File:** `src/bootstrap/state.ts`

Global `STATE` object holds:
- `totalCostUSD: number` — cumulative USD cost this session
- `modelUsage: { [modelName: string]: ModelUsage }` — per-model breakdown

`ModelUsage` tracks:
- `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`
- `webSearchRequests`
- `costUSD`
- `contextWindow`, `maxOutputTokens` (context limits for the model)

### 2.2 Accumulation Pipeline

**File:** `src/cost-tracker.ts`, line 278–323 (`addToTotalSessionCost`)

Called after every successful API response. Pipeline:

1. `addToTotalModelUsage(cost, usage, model)` — accumulates tokens per model
2. `addToTotalCostState(cost, modelUsage, model)` — stores into `STATE`
3. OpenTelemetry counters updated:
   - `getCostCounter().add(cost)` — USD cost
   - `getTokenCounter().add(input_tokens, { type: 'input' })`
   - `getTokenCounter().add(output_tokens, { type: 'output' })`
   - `getTokenCounter().add(cache_read, { type: 'cacheRead' })`
   - `getTokenCounter().add(cache_creation, { type: 'cacheCreation' })`
4. Advisor model usage is also tracked separately via `getAdvisorUsage(usage)` and recursively calls `addToTotalSessionCost`

### 2.3 USD Cost Calculation

**File:** `src/utils/modelCost.ts`, line 131–142

```typescript
function tokensToUSDCost(modelCosts: ModelCosts, usage: Usage): number {
  return (
    (usage.input_tokens / 1_000_000) * modelCosts.inputTokens +
    (usage.output_tokens / 1_000_000) * modelCosts.outputTokens +
    ((usage.cache_read_input_tokens ?? 0) / 1_000_000) * modelCosts.promptCacheReadTokens +
    ((usage.cache_creation_input_tokens ?? 0) / 1_000_000) * modelCosts.promptCacheWriteTokens +
    (usage.server_tool_use?.web_search_requests ?? 0) * modelCosts.webSearchRequests
  )
}
```

All four token types have distinct price multipliers. Cache reads are cheapest, cache writes are more expensive than base input.

### 2.5 Session Persistence

**File:** `src/cost-tracker.ts`, line 143–175 (`saveCurrentSessionCosts`)

## 3. How Cached Tokens Count

### 3.1 Toward Cost

All cache token types are billed and tracked separately:
- `cache_read_input_tokens` — billed at 10% of standard input rate (cheapest)
- `cache_creation_input_tokens` — billed at 125% of standard input rate (write cost)

Both are fully accumulated in `ModelUsage` and included in the `formatTotalCost()` display output.

### 3.2 Toward Context Window Size

For the purpose of **autocompact threshold decisions** (`tokenCountWithEstimation`), cache tokens ARE included:

```typescript
// src/utils/tokens.ts:46-53
return (
  usage.input_tokens +
  (usage.cache_creation_input_tokens ?? 0) +
  (usage.cache_read_input_tokens ?? 0) +
  usage.output_tokens
)
```

This reflects reality — cached content IS present in the context even if served cheaply.

### 3.3 Toward API-Side Task Budget

For the `task_budget.remaining` countdown (see section 4), cache tokens are **excluded**. Only `input_tokens + output_tokens` count (`finalContextTokensFromLastResponse` in `src/utils/tokens.ts:79–112`). This matches `renderer.py:292` server-side.

### 3.4 Toward Subscription Limits (Weekly/Session)

The API manages this server-side via response headers. CC reads utilization from:
- `anthropic-ratelimit-unified-5h-utilization` (5-hour session limit)
- `anthropic-ratelimit-unified-7d-utilization` (7-day weekly limit)
- `anthropic-ratelimit-unified-overage-status` (extra usage / overage)

CC does **not** know the raw token count of these limits. It only receives the utilization fraction (0–1). Whether cache tokens count toward these limits is determined server-side and not visible in the client source.

### 3.5 Token Count for the `countTokensViaHaikuFallback` Function

**File:** `src/services/tokenEstimation.ts`, lines 319–324

When doing actual token counting via the API (not rough estimation):
```typescript
return inputTokens + cacheCreationTokens + cacheReadTokens
```
Cache tokens ARE included in the returned count because this is measuring context window occupancy.

## 4. Local Token Budget System

### 4.1 User-Specified Budget (`+500k` syntax)

**File:** `src/utils/tokenBudget.ts`

Users can write `+500k`, `spend 2M tokens`, or `use 1B tokens` in their prompt. This is parsed by `parseTokenBudget()` using three regex patterns:
- `SHORTHAND_START_RE`: `/^\s*\+(\d+(?:\.\d+)?)\s*(k|m|b)\b/i` — anchored to start
- `SHORTHAND_END_RE`: trailing `+500k` at end of message
- `VERBOSE_RE`: `\b(?:use|spend)\s+(\d+(?:\.\d+)?)\s*(k|m|b)\s*tokens?\b/i`

Multipliers: `k=1000`, `m=1_000_000`, `b=1_000_000_000`.

**File:** `src/screens/REPL.tsx`, lines 2893–2895

At the start of each user turn:
```typescript
const parsedBudget = input ? parseTokenBudget(input) : null;
snapshotOutputTokensForTurn(parsedBudget ?? getCurrentTurnTokenBudget());
```

This snapshots the current total output tokens and sets the budget for the turn.

### 4.2 Budget Tracking

**File:** `src/bootstrap/state.ts`, lines 724–743

```typescript
let outputTokensAtTurnStart = 0
let currentTurnTokenBudget: number | null = null

export function getTurnOutputTokens(): number {
  return getTotalOutputTokens() - outputTokensAtTurnStart  // delta since turn start
}
export function getCurrentTurnTokenBudget(): number | null {
  return currentTurnTokenBudget
}
export function snapshotOutputTokensForTurn(budget: number | null): void {
  outputTokensAtTurnStart = getTotalOutputTokens()
  currentTurnTokenBudget = budget
  budgetContinuationCount = 0
}
```

Budget tracks **output tokens only** (tokens generated this turn), not input/cache.

### 4.3 Budget Decision Logic

**File:** `src/query/tokenBudget.ts`, line 45–93 (`checkTokenBudget`)

Called after each agentic loop iteration. Logic:
1. If `agentId` is set (subagent) or `budget === null` or `budget <= 0`: stop immediately (no budget for subagents)
2. Compute `pct = (turnTokens / budget) * 100`
3. Compute `isDiminishing`: continuation count >= 3 AND delta tokens < 500 for two consecutive checks
4. If not diminishing AND `turnTokens < budget * 0.9` (90% threshold): **continue**, inject nudge message
5. If diminishing OR completed: **stop**

Constants:
- `COMPLETION_THRESHOLD = 0.9` (stop when at 90% of budget)
- `DIMINISHING_THRESHOLD = 500` (early stop if getting < 500 tokens per continuation)

### 4.4 Continuation Nudge Message

**File:** `src/utils/tokenBudget.ts`, line 66–72

```typescript
export function getBudgetContinuationMessage(pct, turnTokens, budget): string {
  return `Stopped at ${pct}% of token target (${fmt(turnTokens)} / ${fmt(budget)}). Keep working — do not summarize.`
}
```

This message is injected as a synthetic user message to continue the model. The model also sees a system prompt section (`'token_budget'`) explaining the behavior (from `src/constants/prompts.ts:546`).

### 4.5 API-Side Task Budget (Separate System)

**File:** `src/services/api/claude.ts`, lines 473–501 (`configureTaskBudgetParams`)

Distinct from the `+500k` local budget. This is an API feature (`output_config.task_budget`, beta `task-budgets-2026-03-13`):

```typescript
outputConfig.task_budget = {
  type: 'tokens',
  total: taskBudget.total,
  ...(taskBudget.remaining !== undefined && { remaining: taskBudget.remaining }),
}
```

Sent via CLI flag `--task-budget <tokens>`. The API uses this to let the model pace itself across tool loops. Only available for 1P (first-party) builds.

**File:** `src/query.ts`, lines 282–291, 504–515

After each compaction, `taskBudgetRemaining` is decremented:
```typescript
const preCompactContext = finalContextTokensFromLastResponse(messagesForQuery)
taskBudgetRemaining = Math.max(
  0,
  (taskBudgetRemaining ?? params.taskBudget.total) - preCompactContext,
)
```

This is needed because after compaction the server loses the context history and can't accurately count spent tokens — the client tells it what was compacted away.

## 5. API-Side Rate Limits and Weekly Limit System

### 5.1 CC Has No Knowledge of Raw Token Limits

CC does **not** know the raw token quota (e.g., "X million tokens per week"). The weekly/session limits are managed entirely server-side. The client only receives:

- `anthropic-ratelimit-unified-status`: `'allowed'` | `'allowed_warning'` | `'rejected'`
- `anthropic-ratelimit-unified-5h-utilization`: float 0–1
- `anthropic-ratelimit-unified-7d-utilization`: float 0–1
- `anthropic-ratelimit-unified-representative-claim`: which limit type applies (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `overage`)
- `anthropic-ratelimit-unified-reset`: unix timestamp

**File:** `src/services/claudeAiLimits.ts`, lines 164–179 (`extractRawUtilization`)

### 5.2 Limit Types

**File:** `src/services/claudeAiLimits.ts`, lines 29–35

```typescript
type RateLimitType =
  | 'five_hour'        // "session limit"
  | 'seven_day'        // "weekly limit"
  | 'seven_day_opus'   // "Opus limit"
  | 'seven_day_sonnet' // "Sonnet limit"
  | 'overage'          // "extra usage limit"
```

### 5.3 Early Warning System

**File:** `src/services/claudeAiLimits.ts`, lines 52–70

CC implements two early warning mechanisms:

**1. Header-based (preferred):** Server sends `anthropic-ratelimit-unified-{5h|7d}-surpassed-threshold` header.

**2. Time-relative fallback (client-side):**
- 5h window: warn if utilization >= 0.9 AND <= 72% of time window elapsed
- 7d window: three thresholds:
  - 75% usage AND <= 60% of week elapsed
  - 50% usage AND <= 35% of week elapsed
  - 25% usage AND <= 15% of week elapsed

These catch users burning quota faster than sustainable.

### 5.4 Overage / Extra Usage

When the main subscription is rejected but overage is enabled:
- `isUsingOverage = (status === 'rejected') && (overageStatus === 'allowed' || overageStatus === 'allowed_warning')`
- CC switches to overage mode transparently
- Overage is metered separately; reasons for disabling are tracked in `OverageDisabledReason` type

### 5.5 Usage API Endpoint

**File:** `src/services/api/usage.ts`

Separate REST endpoint (`/api/oauth/usage`) returns:
```typescript
type Utilization = {
  five_hour?: RateLimit | null
  seven_day?: RateLimit | null
  seven_day_oauth_apps?: RateLimit | null
  seven_day_opus?: RateLimit | null
  seven_day_sonnet?: RateLimit | null
  extra_usage?: ExtraUsage | null
}
```

Where `RateLimit = { utilization: number | null, resets_at: string | null }`. This is used by the Settings > Usage screen.

## 6. Relationship Between Local Counting and API-Side Limits

### 6.1 Local Tracking (What CC Counts)

CC tracks these for its own display and cost estimation:
- Running USD cost per session (per model)
- Token counts (input, output, cache read, cache write) per model
- Session duration (API + wall clock + tool execution)
- Lines of code added/removed

### 6.2 API-Side Tracking (What Anthropic Counts)

The server independently tracks consumption toward limits. CC does not submit token counts — the server derives them from the API calls themselves.

### 6.3 The Decoupling

Local cost (`addToTotalSessionCost`) and rate limit state (`extractQuotaStatusFromHeaders`) are completely separate:
- Local cost: calculated from `usage.*_tokens * price` locally
- Rate limit utilization: read from response headers, no local calculation involved

There is no mechanism to influence the server's rate limit counting from the client. The client is purely reactive — it reads headers and shows warnings/errors.

## 7. Token Optimization Strategies in CC

### 7.1 Prompt Caching

**File:** `src/services/api/claude.ts`, lines 333–374

CC aggressively uses `cache_control: { type: 'ephemeral' }` markers. The `getCacheControl()` function supports:
- Standard ephemeral cache (5-minute TTL)
- 1-hour TTL: `{ type: 'ephemeral', ttl: '1h' }` — for eligible users (Ant internal or subscribers not in overage)
- Global scope: `{ type: 'ephemeral', scope: 'global' }` — for cross-user caching

Eligibility for 1h TTL is **latched session-stable** to avoid busting the cache mid-session if overage status changes.

**Env vars to disable:**
- `DISABLE_PROMPT_CACHING` — global disable
- `DISABLE_PROMPT_CACHING_HAIKU` — disable for small/fast model
- `DISABLE_PROMPT_CACHING_SONNET` — disable for Sonnet
- `DISABLE_PROMPT_CACHING_OPUS` — disable for Opus

### 7.2 Tool Result Budget (Content Truncation)

**File:** `src/query.ts`, lines 379–394

Before each API call, `applyToolResultBudget()` enforces a per-message budget on tool result size. Oversized tool results are truncated and a replacement record is stored. This prevents huge bash outputs or file reads from inflating the context window unnecessarily.

### 7.3 Autocompact / Microcompact

When context exceeds a threshold (measured by `tokenCountWithEstimation`), CC compacts the conversation:
- **Autocompact**: full conversation summary, then restart
- **Microcompact**: per-tool-use compaction, replacing verbose tool results with summaries
- **Cached microcompact**: uses cache editing beta to surgically replace content without breaking the cache

### 7.4 Media Item Stripping

**File:** `src/services/api/claude.ts`, line 956–1015 (`stripExcessMediaItems`)

Limits images + documents per API request to `API_MAX_MEDIA_PER_REQUEST`. Oldest media is stripped first to preserve recent context.

### 7.5 Thinking Block Clearing

When >1h since last API call (confirmed cache miss), `thinkingClearLatched` triggers clearing of thinking blocks from prior tool loops. This reduces context size when the extended thinking cache has already expired anyway.

### 7.6 Context Collapse and History Snip

Two additional experimental features:
- `HISTORY_SNIP`: removes older turns from the message window
- `CONTEXT_COLLAPSE`: collapses expanded context back to a smaller form

Both operate before autocompact to avoid triggering the more expensive full compaction.

### 7.7 Max Output Tokens Capping

**File:** `src/utils/context.ts`, lines 22–26

```typescript
export const CAPPED_DEFAULT_MAX_TOKENS = 8_000
export const ESCALATED_MAX_TOKENS = 64_000
```

Default `max_tokens` is capped at **8,000** (far below the 64k model max) for slot reservation optimization. The p99 output is ~5k tokens, so 32k/64k defaults over-reserve slot capacity. When output is truncated by the cap, a retry at 64k is attempted.

## 8. The `costHook.ts` / `useCostSummary`

**File:** `src/costHook.ts`

```typescript
export function useCostSummary(getFpsMetrics?: () => FpsMetrics | undefined): void {
  useEffect(() => {
    const f = () => {
      if (hasConsoleBillingAccess()) {
```

- Total cost in USD
- Total API duration and wall-clock duration
- Lines added/removed

## 9. Can Hooks Influence Token Usage or Budgets?

### 9.1 External Hook System (CC Hook Events)

CC's external hook system (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`) runs as ephemeral processes and communicates via stdio. These hooks can:
- **Block or approve** tool use (affects which tools run, not token counts directly)
- **Modify the stop behavior** via `Stop` hook
- **Inject content** into the user prompt via `UserPromptSubmit` hook (which would ADD tokens)

Hooks cannot:
- Read or modify `tokenBudget` / `taskBudget` state
- Access `addToTotalSessionCost` or any cost state
- Influence `max_tokens` or `cache_control` parameters

### 9.2 Token Budget and Hook Interaction

The `+500k` budget is parsed from user input in `REPL.tsx` before the query is dispatched. A `UserPromptSubmit` hook that modifies the prompt COULD in theory inject or remove the budget syntax, but the budget is read from the original user input, not the hook-modified version. (This would require verifying against the hook implementation in `src/adapters/cc-hooks/`.)

### 9.3 SDK Hooks (Registered Callbacks)

SDK-registered hooks (`registeredHooks` on `STATE`) can intercept events like `PreToolUse` and `PostToolUse` via callbacks. Same constraints apply — they can influence tool approval but not the cost/budget state directly.

## 10. Key Implementation Notes for Claudex

### 10.1 What CC Reports vs. What API Tracks

CC's local tracking is **display-only** — it has no feedback effect on API quotas. The API counts tokens from the actual API calls.

### 10.2 Cache Token Cost Separation

Cache reads are charged at ~10% of input rate. Cache writes at ~125% of input rate. If Claudex wants to estimate true cost impact of its context injection, it needs to distinguish whether tokens will be cache hits (cheap) vs. cache misses (full rate). This requires knowing the cache state, which CC doesn't expose to hooks.

### 10.3 Weekly Limit Structure

There are separate per-model limits (`seven_day_opus`, `seven_day_sonnet`) in addition to the aggregate weekly limit. An optimizer trying to conserve weekly quota should prefer cheaper models (Haiku → Sonnet → Opus) and cache-read-heavy patterns.

### 10.4 The `finalContextTokensFromLastResponse` vs. `getTokenCountFromUsage` Distinction

Critical for any system that tracks token consumption:
- Use `getTokenCountFromUsage` (includes cache) for: context window threshold checks, space remaining in context
- Use `finalContextTokensFromLastResponse` (excludes cache) for: task budget remaining calculations, matching server-side budget arithmetic

### 10.5 The `roughTokenCountEstimation` Fallback

Used when no API usage data is available (new messages added since last API call). 4 bytes/token for text, 2 bytes/token for JSON, 2000 tokens flat for images/documents. These estimates err conservative (overestimate tokens) to trigger compaction early rather than late.
