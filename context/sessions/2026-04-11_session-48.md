# Session 48: Reranker supervisor — silent failure + CWD root cause

## Flow
Entered investigating "1 err(5m)" on the status line and a claim that Claudex was broken. The error count turned out to be benign bash exit-code noise from my own diagnostic commands. The real finding was a flood of `⚠ Services down: Reranker ... Auto-restart attempted` advisories — **1,241 over 10 days, 285 in the last 24h** — pointing at a reranker that had been dead the whole time. The "Auto-restart attempted" string was a hardcoded lie: `heartbeat.ts` concatenated it into every advisory regardless of whether any restart was attempted, because the heartbeat had explicitly delegated reranker restart to `RerankerSupervisor` — which was only ever called once at Angel boot and had no recovery path after that. Root-caused the supervisor's two terminal exit states (externally-managed-with-no-retry, and spawn-failed-with-no-retry), fixed them with `ensureRunning()` + cool-down + honest per-service outcomes + log-stream idempotence + 30s→60s health-timeout bump. Committed as `73b213e` after full-suite verification and live end-to-end recovery test (killed external reranker → next heartbeat tick downgraded + respawned + sent no fake advisory).

Then the hardening pass on "make sure this doesn't happen again" turned up a worse bug hiding in plain sight: `index.ts` was passing `projectRoot: process.cwd()` to the supervisor, but the session-start hook spawns Angel with `cwd: os.homedir()` for security. Which means **every auto-spawned Angel since the supervisor was introduced was looking for `~/services/reranker.py`, not finding it, throwing "script not found", and silently falling back to bi-encoder retrieval.** The only reason the reranker ever worked was that the user (or I) occasionally started Angel manually from the repo directory. Fixed via `__dirname`-based resolution. Also closed the PID-file write race (claim-first semantics) and added a services-down interval override so dead-service recovery isn't gated on the 10–30 min idle backoff. Live-verified by booting Angel from `~` — supervisor resolved the correct path, reranker spawned, health probe passed in 31s.

## Decisions
- **`ensureRunning()` is the heartbeat's recovery hook**, not a new supervisor polling loop. Delegating to the existing heartbeat tick avoided a second timer and gave recovery the same cadence as service-health checks. The override-on-down intervalpin guarantees recovery latency stays bounded even under idle backoff.
- **Claim-first PID file ordering** — the semantic change from "Angel is fully booted" to "an Angel is booting or running" is intentional. A partially-booted Angel showing as running in the PID file is the right signal to rival spawn attempts; the `main().catch` already releases the PID file on fatal error.
- **Externally-managed downgrade resets `restartCount`** — conceptually a new lifecycle, so the fresh restart budget is correct. Without this, a long-running external instance that died once would consume one of the 3 restart slots against the subsequent managed lifecycle.
- **Didn't add log rotation, Python discovery hardening, or HF offline mode** — scope lock; these are speculative improvements, not active bugs.

## Learnings
- "Advisory message says X happened" is not evidence X happened. Search for the string: if it's a static concatenation rather than a templated outcome, the advisory is lying by construction. This one had been lying for 10 days and ~1,200 messages.
- CWD-dependent path resolution is a Windows/cross-directory gotcha: `process.cwd()` feels stable until you remember that detached subprocess spawns often set CWD intentionally (security, filesystem isolation). Bundle-relative paths via `__dirname` are the CWD-independent answer for anything a long-lived daemon needs to find.
- When the heartbeat delegates a duty to another subsystem ("supervisor owns restart now"), verify the other subsystem actually has a recovery loop. Delegation with no receiver is just dropping the ball and printing the wrong log line.
